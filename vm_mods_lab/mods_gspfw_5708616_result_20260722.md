- Isolated VM only; RTX 5090 remained assigned to the VM through vfio-pci.
- No NVIDIA driver was installed in the guest or host.
- Official NVIDIA Linux 570.86.16 package was downloaded and extracted only.
- The test used MODS `-notest` bring-up parameters already used for prior GSP checks.

sudo timeout 160s ./mods -no_net -nc -mle_disabled gputest.jse \
  -no_gold -notest \

  -devid_check_ignore -vfe_version_check_ignore \

  -gspfw /mnt/fw57086/gsp_ga10x_570.86.16.bin

Result:
- Exit code: `139` (`SIGSEGV` after MODS error cleanup).
- MODS successfully opened the supplied GSP file.
- MODS rejected it before GSP-RM initialization:

```text
NVRM: <func>: GSP firmware image version mismatch: got version 570.86.16, expected version 570.89
NVRM: <func>: Error preparing GSP-RM image
NVRM: <func>: Cannot initialize GSP firmware RM
Error 000000000682 : Gpu.Initialize NVRM invalid data
SIGSEGV
```

Safety checks:
- BAR0 snapshot before/after showed no diff in the tracked fields.
- Guest dmesg showed the MODS diagnostic driver opening/enabling/disabling/closing the device, without XID/AER-like GPU fault logs.
- Host still reported the RTX 5090 bound to `vfio-pci` after the test.
- Host dmesg showed vfio reset/enable records, but no NVIDIA XID or PCIe AER fault for this attempt.

Conclusion:
- Public `570.86.16` does not satisfy this MODS build.
- Together with previous `570.144` and `610.43.03` attempts, the blocker is now confirmed as exact GSP `.fwversion == 570.89`, not file path, ISO delivery, or basic GSP ELF format.
- Practical next paths are to find a GSP file whose `.fwversion` is exactly `570.89`, or find a MODS/RM build whose expected GSP version matches a public GB202-capable firmware.

Additional check: `-gsp_disable`

Command:

```sh
sudo timeout 140s ./mods -no_net -nc -mle_disabled gputest.jse \
  -no_gold -notest \
  -adc_cal_check_ignore -adc_temp_err_check_ignore \
  -devid_check_ignore -vfe_version_check_ignore \
  -timeout_ms 5000 -fslib_mode_debug -fsp_poll_timeout_ms 16000 \
  -skip_azalia_init -disable_composition_mode -null_display \
  -gsp_disable
```

Observed log:

```text
NVRM: <func>: GSP is disabled.
NVRM: <func>: FSP has clock boost capability
NVRM: <func>: Loading GSP image for monolithic RM using FSP.
SIGSEGV
```

Interpretation:
- `-gsp_disable` is not a clean CPU-only fallback on this GB202/MODS build.
- It disables GSP-RM mode, but the path still needs a GSP-side image for monolithic RM through FSP.
- This explains why public logs showing `GSP-RM : Disabled` do not by themselves prove a package can initialize GB202 without matching internal firmware resources.
