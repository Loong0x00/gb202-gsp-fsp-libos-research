# AES0/kslot 解密 oracle 尝试记录（615.78.08）

日期：2026-10-27。范围：离线静态分析、公开源码/网络检索；未向 AES 引擎或 FSP_RUN 发送数据，未执行新的 GPU 实验。

## 已确认

615 主 GSP-RM 中保留 AES0/AES1、Keyop、kslot、AES-GCM 客户端痕迹。与 610 `gsp_inner_19f040_a.elf` 对照，以下关键函数存在**逐字节相同**的实现：

| 作用 | 615 VA |
|---|---:|
| 16 字节 keyslot 写入/清零 helper（逻辑偏移 0x101c–0x1028） | `0x1c3b87e` |
| keyslot 装载入口 | `0x1c3d39a` |
| A/B 槽与 digest 校验编排器 | `0x1c3d460` |
| keyslot 读取路径 | `0x1c3c566` |

这说明 AES0/kslot 路线有真实代码基础，不只是字符串相似。

## 尚未证明

1. **尚未完成一次已知输入、已知输出的 AES 操作。** 没有证据表明目前能由 host 直接调用这套客户端并取得输出。
2. **逻辑偏移不是物理 BAR 地址。** `0x101c–0x1028` 经过运行期 engine descriptor 和 aperture 映射，不能当成 `BAR0+0x101c` 使用。
3. **slot 归属未知。** 没有证据证明这些 slot 与 `FSP_RUN` 的 AES-256-GCM data key 共用或可被 GSP 使用。
4. **615 没有现成任意函数调用路径。** 旧 K3 的 33 元素 staging 溢出和 rxrefresh 回调已在 615 协议改版中消失；`GPU_EXEC_REG_OPS` 只允许寄存器读写，不是通用函数调用。
5. **QEMU 当前不能补足该环境。** 本地 GSP QEMU 尚未启动完整 GSP-RM 任务，无法直接复用自然启动时的 AES descriptor。
6. **公开资料未给出可用映射。** 本地公开头文件、MODS RegHal 和网络检索均未闭合 AES0 的物理寄存器地图。

## 已排除的无效捷径

- 直接把旧 610 函数地址用于 615：不可行，必须使用上述 615 地址。
- 把 `0x101c` 当作绝对 BAR0 地址：错误，属于逻辑 aperture 偏移。
- 用 `nvidia-smi`/NVML 或 `EXEC_REG_OPS` 调用 AES 函数：不支持，后者只做寄存器读写。
- 用 `0x8f4xxx` 的历史初始化图案直接认定 keyslot：证据不足；其中 `0x8f601c=0x300`、`0x8f701c=0x103` 只是现存读数，不能据此命名或当作密钥。

## 下一步的硬门槛

继续这条路线必须先满足至少一项：

1. 获得一个**自然运行中的 AES descriptor/上下文**，从而复用现有客户端并读回输出；或
2. 在 615 上建立一个新的、受控的 GSP 函数调用能力；或
3. 使用 610 已有的 K3 原语先做**路线可行性验证**，再决定是否值得为 615 重建调用路径。

在上述门槛未满足前，不应把 `FSP_RUN` 当测试输入，也不应声称 AES0/kslot 已成为解密 oracle。
