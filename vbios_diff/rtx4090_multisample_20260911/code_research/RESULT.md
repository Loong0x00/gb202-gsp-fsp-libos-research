# RTX4090 Falcon 离线函数级差分

## 结论（重要新增反证）

在本任务执行期间 collector 新增了 `collector/roms/github_asus_strix_3c.rom`。只读解析得到版本 **95.02.3C.40.FB**，sign-on `RTX4090 VB Ver 95.02.3C.40.AS19`。它和候选 `95.02.3C.00.02` 的 **app01、app07、app08 IMEM 全部逐字节一致**，并非仅归一化相似；app01、app07 DMEM 也一致。app08 DMEM 同长35920字节，357字节不同。

因此，下列 ASUS 95.02.18.80.87 → 48候选的代码变化，**不能视作48候选独有补丁**。它们同样存在于该ASUS 3C分支文件。新的对照并非完整版本号相同，且GitHub文件标称板型/原厂24GB属性未在本任务独立认证，不能由此证明该对照不能支持48GB；但是“48候选含有独有明文Falcon解锁代码”的论断已无此差分支持。

所有offset以下均为各app的 **IMEM内偏移**，不是ROM绝对偏移。保留app08原ID，不赋予未经证实的正式用途名称。

## 最值得跟进的内存相关代码（非独有解锁代码）

### A. app08 / target01：F_30f2 → F_3179 中新增表项控制的位操作

候选函数区间 `[0x30f2,0x5bc5)` → `[0x3179,0x5c82)`；直接调用入口可见于 `0x656b → 0x6628`。该函数很大，不能将其中每个块假定为独立函数。

旧局部 `[0x5679,0x56c3)`，新局部 `[0x5700,0x5780)`。旧代码在 `0x56ab/0x56b0` 将表值写到 `D[0x149a0450]` 后继续；新代码在 `0x5733` 写入后，增加 `0x5735..0x5759`：

```text
selector = sign_extend_8(D8[0x70c2]);
if (D8[0x4898 + selector] == 1 && !(D32[0x1417e318] & 0x10)) {
    D32[0x1417e318] |= 0x10;      // 0x574a, 0x574d
    D32[0x149a0450] &= 0xff7fffff; // 0x5751, 0x5756, 0x5759
}
```

这里是具体条件、掩码和读改写的变化，**不是跳转目标重定位**。本地rnndb将0x17e000归为PMFB广播区，将0x9a0000归为Pascal起PBFB广播区，故优先级高于单纯“出现24/48常数”的猜测。D地址0x14000000前缀按重复访问模式推测为寄存器访问窗口；本任务未找到可直接认证Ada该窗口和上述两个位含义的公开头文件，因此**不得命名为rank/clamshell/容量开关**。

特别提醒：原始文本diff看起来删除0x9a0400写入，但新代码 `0x5718` 从0x149a0410开始，`0x571f` 减0x10，`0x5722` 仍写0x149a0400；不可把寄存器分配/地址构造变化当成删除。0x9a2580/2584/2588也应跟踪寄存器算术，不能只比mov立即数。

新增表条件的0x4898区与0x70c2字节，在本次候选/ASUS3C对照的DMEM里也没有差异；但其运行时来源和更新链尚未追完。代码一致不代表不同板上分支执行结果一致。

### B. app08：两个短函数删除成对控制位操作

* `[0x2cf7,0x2d1d)` → `[0x2d98,0x2db0)`：仍对 `D32[0x1417e318] &= ~0x11`，但删除旧 `0x2d08..0x2d19` 对 `D32[0x1417e21c] &= ~1`。
* `[0x2d1d,0x2d6d)` → `[0x2db0,0x2df4)`：删除旧 `0x2d5a/0x2d64..0x2d69` 的 `D32[0x1417e21c] |= 1`。

成对删除发生于同一PMFB地址附近，可列为内存控制序列变化候选；没有Ada字段定义支撑，不能解释成单双面/容量控制。新ASUS3C对照含同一代码。

### C. PRE_OS app01：明确的rank/bank字段读取，核心逻辑没有改变

所在候选函数 `[0x3fa6,0x4223)` → `[0x3fb5,0x424c)`。旧 `0x4103..0x414a` → 新 `0x4126..0x416d`：

* 读取 `D32[0x149a0200]`，随后读取+4。
* 提取+4寄存器的bits24:25，分支取4/8/16。
* 提取首寄存器bit2，形成1或2。
* 随后算出前者×12，并调用旧0x8af4 → 新0x9b0c。

rnndb `gf100_pbfb.xml` 的CFG0 bit2叫RANKS，CFG1 bits24:25叫BANKBITS，与指令字段精确吻合；但Ada沿用程度仍需验证。**上述读取、分支值和算术在两版相同，只是地址平移+0x23及callee重定位**。这比把某个0x18→0x30常数解释为容量更可信，也说明至少这段拓扑处理不是新增48G逻辑。

### D. 不应当作BAR1容量变化：共享尾部函数的scratch写入

app01 `[0x88ed,0x894a)` → `[0x98e0,0x994c)`；app08对应 `[0xdbaa,0xdc07)` → `[0xf072,0xf0de)`。

新增读取Falcon `I[0x25c]`，将所得值写入 `D[0x14001470]`（app08 0xf080/0xf083及0xf0c3..0xf0d2）。Ada `dev_bus.h` 定义 `NV_PBUS_SW_SCRATCH(i)=0x1400+i*4`，0x1470落在scratch[28]，**不是已知BAR1尺寸寄存器**。该变化跨app重复，更符合共享运行库/状态记录变化；I[0x25c]的语义未确认。

## BAR1结论边界

未在本次有限代码检索中确证设置32GB BAR1上限或24→48GB FB的函数。不能据未命中固定立即数证明不存在：地址可能经间接构造，尺寸可能来自DMEM/外部表、PCIe能力或其他阶段。

本地驱动 `src/nvidia/src/kernel/gpu/bus/kern_bus.c:546-576` 分别从PCI BAR大小和registry override确定BAR1 aperture；`bus/arch/turing/kern_bus_tu102.c:396-437` 独立比较FB与BAR1可映射大小。因此文章“48GB FB但32GB BAR1”不要求二者由同一个Falcon容量常数控制。此处仅使用已存在本地文件，没有访问链接/网络或设备。

## 函数级归一化方法及限制

`analyze.py`：去掉地址列、原始编码列及envydis C/B标志；先将直接call/bra/lbra的最后一个目标操作数替换为占位以建立全指令序列对应，再由匹配的指令地址验证目的地映射；只有映射支持的目标平移才从差分中排除。无法验证的目标另列 `target_unverified`，不冒充语义变化。数据立即数不清零，不掩盖掩码/常数变化。

函数入口为直接调用目标、入口0以及部分return/exit之后的候选边界；不是符号级/CFG证明。存在间接调用、跳表、尾调用、内联大函数和边界错配；低相似度/多对一匹配只作导航，不可视作已确认同一函数。寄存器重分配及DMEM地址布局变化也仍保留，不等于行为变化。

|01|278/318|273|150|1963|

无剩余文本差异不能等同可证明语义一致；同地址目标在版本间也可能对应不同代码。最强一致性证据仍是新3C对照的完整IMEM逐字节相等。
