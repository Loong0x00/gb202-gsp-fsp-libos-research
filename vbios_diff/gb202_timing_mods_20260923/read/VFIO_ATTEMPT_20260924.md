# GB202 MODS read probe: attempted handoff, aborted before VM/GPU test

Host date: 2026-09-24 (local). This document records the **first, failed handoff only**; it is not a recipe to retry an unsafe transition. The user's subsequent authorization led to a separate manual handoff and a successful **read-only broadcast CONFIG0..5** capture; see `GB202_MODS_LIVE_READ_20260924.md`. Do not treat the statement below "no GPU VM was started" as the final result of the full task.

## Preserved Quill and rehearsal

- `/home/user/quill/README.md` confirms persistent `quill-kernel` owns PTYs and graphical `quill` is a disposable view. Live Pi processes were in `quill-kernel.service` cgroup, and an independent SSH `quill-attach` was active in remote session 8; `loginctl show-user user` had `Linger=yes`.
- A **no-GPU, no-network** disposable Ubuntu VM was booted twice to rehearse the text probe. The correct MODS 570.215 executable existed at `/home/mods/570.215/mods`; a matching 5.15.0-119-generic `mods.ko` from `vm_mods_lab/mods-extra-v5-20260829.iso` loaded inside that disposable guest. Its JS file was loaded and reached `Gpu.Initialize()`, which returned `Gpu.Initialize invalid object property` in the **no-GPU** guest. This does not verify the real-GPU readback path. Both no-GPU VMs were stopped over QMP and their child overlays passed `qemu-img check` (the second was stopped before a check of its child). These rehearsals did not pass through or access the host NVIDIA device.

## Actual attempted host handoff

- User confirmed the graphical desktop was unused. Original GPU `0000:01:00.0` belonged to NVIDIA, audio `0000:01:00.1` to snd_hda_intel; exactly those two devices in IOMMU group 13. SSH, quill-kernel and quill-appserver were active, and a remote quill-attach session existed.
- Executed the already-existing guarded `/home/user/rt_5090_project/vfio_production_lab/host/rtx5090-vfio-enter-live`. It stopped GDM/seat0 session and entered module unload, but **failed at `nvidia_modeset`: `modprobe: FATAL: Module nvidia_modeset is in use.`** Its failure handler printed `ENTER_FAIL rc=1` twice, including a message refusing to restart GPU clients while module removal was in flight. This is a failed transition, **not a successful VFIO handoff**. No QEMU GPU VM, MODS on real GPU, register read, or timing write was run.
- Immediate readback showed the GPU/audio still bound to `nvidia`/`snd_hda_intel`, no armed marker, SSH/Quill survived; `nvidia_drm` was missing and `nvidia_modeset` still referenced, with `nvidia-persistenced` holding `/dev/nvidia-modeset`. Read-only journal follow-up established: the script stopped `nvidia-persistenced` at **01:44:47**; it **restarted at 01:44:57** along with LACT, before kernel logged `nvidia-drm` unloading at **01:45:07**; GDM was restarted at 01:45:07. This supports a rollback/service-restart-versus-module-unload race and makes `nvidia-persistenced` a concrete candidate for holding `nvidia_modeset` when removal failed. But no exact FD/refcount snapshot exists **at the failing modprobe**, so the original holder/first trigger cannot be proved exclusively from logs. Do **not** blindly retry.
- Conservatively restored the missing display module with `sudo modprobe nvidia_drm modeset=1 fbdev=1`, then restarted GDM after the first restart had failed to register a greeter. Final `loginctl` showed `gdm-greeter` on seat0; `nvidia-smi` showed NVIDIA driver with display active again. **Original user GNOME session/windows were terminated by the handoff and cannot be automatically resurrected.** SSH `quill-attach`, Pi, quill-kernel, quill-appserver remained alive. `lactd`, `nvidia-persistenced`, and `waterloop-fan-control.service` were active. No PCI bus reset, GPU VFIO bind, VBIOS flash, or timing write was performed.

Earlier immediately after service restart, controller logged radiator `2102 RPM`, pump `3276 RPM`, failures `0/0`. Cooling is under the existing automatic controller; no manual PWM overrides were introduced.
- Before any future direct VFIO/MODS attempt, verify the cooling policy when `nvidia-smi`/hotspot telemetry disappears and the handoff stops `waterloop-fan-control.service`. Preserve verified pump flow and radiator airflow *before* detaching the host driver. Do not proceed by defeating module holder checks or by trial-and-error timing register writes.
