# GB202 GDDR7：MODS 原生 `dramclk(18000)` 下实机时序（2026-09-24）

用户问原先 MODS 14001 MHz 的 CL35 在“18000 的频率下”是多少，并明确授权在隔离 VM 用 MODS 原生功能超显存。**这次读取到了真实升频后活动寄存器；没有推断或手动修改 CL。** 本文件记录目标时钟、实际读回、寄存器与安全恢复。

## 前提 / 命令路径

不需要恢复宿主图形桌面以继续交流。旧客体的 MODS 有时限且已退出，先 QMP 关闭**旧客体**并核实 GPU+音频 `vfio-pci ... reset done`；显卡仍归 VFIO，宿主 GDM、LACT、persistenced 停止，HSR 高频 GPU 采样器被冻结，Quill kernel/appserver 和 SSH 存活。新客体使用独立一次性 qcow2 写层、OVMF 变量和无网络的 MODS 570.215，`mods.js -skip_azalia_init -null_display -no_vga -no_gold -no_test` 初始化 GB202/E0 卡。在 BIOS 自控冷却风扇和水泵转速持续>2k/>3.6k RPM、无工作负载下操作；clock trial 期间启动**独立 30s QMP 紧急复位计时器**。

实机 MODS **570.215** 的交互界面接受 `dramclk(mHz)` 并输出 ClkM 实际/有效 MHz。可读的**570.151** `mods.js` 将此函数实现为 `clk(Gpu.ClkM,mHz)`，再依条件走 PerfPoint/SetClock；但 **570.215 的 `mods.jse` 是加密文件，本次没有独立证实该版本 JS 所走的具体分支**。先执行 `dramclk()`：实际 `14001.00`、有效约 `13968.69` MHz；八 FBPA+广播 CONFIG0..5 的 **54 字**都是

```text
1a6afd4f 796805a3 cc2a0f00 2400004c f1428032 e8027144
```

## 18000 目标的实机结果

直接在 MODS 交互界面执行 `dramclk(18000)`，MODS 回读 **ClkM 实际 17999.00 MHz、有效 17988.52 MHz**。抓取九组 CONFIG0..5 后再次运行 `dramclk()`，仍为 **实际 17999.00 MHz、有效 17964.89 MHz**。差距属于该次 MODS 时钟输出，不能把目标 18000 误说成恰好 18000.00，也不能由此证明稳定性。

在**时钟实际约17999 MHz**的两个时钟读数之间，广播和八个 FBPA **九组全部相同**：

| 寄存器 | 实机原始值 |
|---|---|
| CONFIG0 | `0x1c711054` |
| CONFIG1 | `0x797885a5` |
| CONFIG2 | `0xcc2c1000` |
| CONFIG3 | `0x2400006c` |
| CONFIG4 | `0xf1428032` |
| CONFIG5 | `0xe8027154` |

按已核对 CONFIG0/1 位域：**RC=84、RFC=272、RAS=56、RP=28、CL=37、WL=11、RD_RCD=34、WR_RCD=23**。按旧公开 CONFIG2 位域还可解 `WR=44`，但后续 GDDR7 位域的精确语义未完全验证。六个实机原始值与本卡**旧 E1 VBIOS** `flash_logs/astral-original-20260726_020901.rom` 的 MEMORY TIMINGS entry15（`0x73681+6+15*105`）**逐字一致**；这是 E0 实机该次 MODS 升频状态的独立交叉检验，不代表 E0、E1 所有条目相同，也不是宿主运行17001 MHz时的读数。

## 为什么 14001→17999 MHz，CL 只从35到37？

**从选择配置字的机制看**，这次切换选了另一条宽频段 VBIOS profile，而不是按目标频率线性插值 CL；但档位机制**不能解释这颗显存为什么物理上可以承受 CL37@17999 MHz，也不能否定 14001 MHz 有显著余量**。已解析的本卡**旧 E1 ROM** Memory Clock 表把 `14750..19999 MHz` 指向 tweak entry15；当前 E0 客体在 17999 MHz 读到的六字恰与 E1 entry15 相同，而 14001 MHz 的字与 E1 entry14 相同。**这仍未直接读出 E0 的 entry index 或实际换档 consumer**；E1 上限19999也不是“经稳定性认证”的证明。

### GDDR7 规范核查后的时钟域换算

以下是恢复宿主显示后的离线规范/数值核查，没有再次操作GPU。GDDR7 不能把 NVIDIA 显示的 `ClkM` 直接当成传统 DDR 的物理命令时钟。Cadence 对 JESD239 时钟模型的说明是：外部高速时钟为 **WCK**，DRAM 内部产生 **`CK4=WCK/4`**，CK4 用作延迟参考；PAM3 模式的一个 256-bit burst 用 8 个 WCK 周期传输。与 JESD239 Table 1 数值一致的公开频率表给出：28 Gb/s 时 **CK4=1.75 GHz、WCK/RCK=7 GHz、DQ=14 GBaud**。本卡标准状态同时满足 NVIDIA 官方 28 Gb/s 规格和 MODS `ClkM=14001 MHz`，因此本卡这个 NVIDIA 数值与 PAM3 baud 数值对应，得到：

```text
有效数据率 ≈ 2 × ClkM
WCK          ≈ ClkM / 2
CK4          ≈ ClkM / 8
```

这里的 `14 GHz ClkM` 只是与 `14 GBaud` 数值对应，**不是 14 GHz 的 WCK**；也不能把 PAM3 简化成“每个物理 symbol 固定携带2 bit”。来源：[Cadence GDDR7 overview](https://community.cadence.com/cadence_blogs_8/b/fv/posts/cadence-introduces-industry-s-first-gddr7-verification-solution)、[JESD239](https://www.jedec.org/standards-documents/docs/jesd239)、[公开频率关系表](https://www.paltek.co.jp/techblog/techinfo/260831_01)、[NVIDIA RTX 5090规格](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5090/)。当前 JEDEC 落地页是后续修订；精确 MR 编码必须按适用修订和 Samsung 器件资料核对。

若 `CONFIG1.CL` 是 CK4 周期数，则其候选时间不是 `CL/ClkM`，而是：

\[
t_{CONFIG.CL}=CL\,t_{CK4}=\frac{8\,CL}{ClkM}
\]

| 状态 | 证据边界 | CK4 | `CONFIG1.CL` 候选时间 |
|---|---|---:|---:|
| 14001 MHz / CL35 | 本次 live | 1.750125 GHz | **19.9986 ns** |
| 14750 MHz / CL37 | 旧 E1 entry15 下沿；非 live | 1.843750 GHz | **20.0678 ns** |
| 17001 MHz / CL37 | 由旧 E1 档位推断；未做17001 live CONFIG读 | 2.125125 GHz | **17.4107 ns** |
| 17999 MHz / CL37 | 本次 live | 2.249875 GHz | **16.4454 ns** |

这个 CK4 解释不只是 CL 一个数的巧合。将已验证的 14001 MHz entry14 与旧 E1 高档下沿14750 MHz entry15按 `CK4=ClkM/8` 换算，RC约45.14→45.56 ns、RFC 144.56→147.53 ns、RAS 30.28→30.37 ns、RP 14.86→15.19 ns、CL 20.00→20.07 ns、RD_RCD 18.28→18.44 ns、WR_RCD 12.57→12.47 ns；多个独立字段同时维持相近绝对时间。结合 CK4 是GDDR7延迟参考，这对 **GB202 CONFIG0/1计数处于CK4域**是强支持。

但证据仍不能把 NVIDIA `CONFIG1[6:0]` 的 **CL** 直接写成“已证实等于 JEDEC MR0.RL”：公开 NVIDIA Memory Tweak 文档只定义该位域名为CL，未给GDDR7单位；尚未读出颗粒MR0，也未闭合GB202换档时由哪个固件把CONFIG字段转换为MRS、RCK前导和控制器流水线设置。上表因此是 **CONFIG.CL域的候选时间**，不是端到端GPU读延迟，也不包含排队、行未命中、RCK启动/前导、PCB往返和控制器流水线。

反过来看用户关心的**低频余量**：CK4的固定比例在相对比较中会抵消，所以先前的比例推导仍成立。若17999 MHz 的 CL37确已通过数据完整性和长时稳定性验证，且相关隐藏profile字段在14001 MHz也能配套，那么同等CONFIG.CL时间折算为 `37 × 14001 / 17999 ≈ 28.8`，约 **CL29**；若以当前宿主17001 MHz但仅推断的CL37计算，则约 **CL30.47**。这说明“可能有显著余量”在数学上成立，**不等于CL29/30已经可写、可训练或稳定**。

17999 MHz目前只有短时寄存器读数，未做数据完整性、CRC/误码或长期稳定测试；旧 E1 表把14750–19999全部指向同一完整entry，而entry14→15有22/105字节变化，不能把CL单项或这个宽频段等同于认证。规范还规定受控WCK频率切换；现有证据支持完整profile/训练路径，不支持运行中只写一个CONFIG1字段。

没有压力测试、未测 ECC/CRC 误码率或长期稳定性；仅可说**短时的寄存器读取成功且时序随原生时钟切换**。

## 回退为什么触发客体复位

向 MODS 发 `dramclk(14001)` 后回读“有效”降到约 `13995.99 MHz`，但“实际”仍报告 `17999.00 MHz`。不能证明硬件已完全退回原始 14001 MHz 工作状态，因此符合预设失败门槛：**立即通过 QMP 关闭客体**，内核确认 GPU/音频都 `vfio-pci ... reset done`。无需关宿主 Pi/SSH，也未向宿主 NVIDIA 驱动交还 GPU。

随后以**全新**客体重新初始化 MODS，确认为 `DRAM Clock 14001 MHz`，原生 `dramclk()` 重新实读实际 `14001.00 MHz`/有效约 `13990.85 MHz`，八 FBPA+广播 54 字全部恢复到升频前的原值、CL35。这个新的基线客体 **仍在运行**，显卡仍属 VFIO；GDM/LACT/persistenced 和自定义散热服务尚未恢复，主板 BIOS 自动 PWM 正在控制冷排/水泵，HSR 采样器仍被冻结。后续若需主机桌面，必须安全 QMP 关客体并按先驱动/散热服务、最后 HSR 解冻的顺序恢复。
