- **PROVED:** The reset-choice strings immediately preceding the marking logs are `bus reset` at VA `0x01e7ec28`, `os reboot` at `0x01e7ec38`, and `unknown` at `0x01e7ec48` (`/tmp/gsp_inner_19f040_a.elf`, VAs just cited).

- **PROVED:** Code at `0x0157b67c` constructs the no-spare log address `0x01e818a0` and passes it as a logging argument (`a2`) before the far call at `0x0157b68a` (`/tmp/gsp_inner_19f040_a.elf`, VA `0x0157b67c..0x0157b692`).

## 2. GB202 chip/HAL binding

- **PROVED:** Current open RM assigns GB202 `ChipHal` index 65: the `arch == 0x1b && impl == 0x2` GB202 branch sets `__nvoc_HalVarIdx = 65` (`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_chips2halspec_nvoc.c:129-132`).
- **PROVED:** The relevant stripped-GSP dynamic constructor reads the chip index, dispatches on `index >> 5`, and for group 2 retains `index & 0x1f` (`/tmp/gsp_inner_19f040_a.elf`, VAs `0x0198c93c..0x0198c950` and group-2 entry `0x0198d010..0x0198d022`).
- **PROVED:** The constructor's object slot `+0x188` is the repair HAL slot. Its group-2 selection tests mask `0x3001`: VAs `0x0198da5a..0x0198da70` form `(0x3001 >> low_index) & 1`. A set bit constructs method VA `0x0156df8c` at `0x0198da74..0x0198da78` and stores it to `+0x188` at `0x0198da7c`. An unset bit branches to `0x0198de56`, constructs VA `0x01975824`, then jumps back to that same store (`/tmp/gsp_inner_19f040_a.elf`, VAs `0x0198da5a..0x0198da7c` and `0x0198de56..0x0198de5e`). Therefore the real implementation is selected only for group-2 low indices 0, 12, and 13.
- **PROVED:** GB202 index 65 is group 2, low index 1; bit 1 of `0x3001` is clear. The constructor therefore binds `+0x188 = 0x01975824`, not `0x0156df8c` (`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_chips2halspec_nvoc.c:129-132`; `/tmp/gsp_inner_19f040_a.elf`, constructor VAs above).
- **PROVED:** VA `0x01975824` is a 16-byte success stub: it creates/removes a 16-byte frame, executes `c.li a0, 0`, and returns at `0x01975830` (`/tmp/gsp_inner_19f040_a.elf`, VAs `0x01975824..0x01975830`).
- **INFERENCE:** Returning zero is `NV_OK` under RM conventions, so a GB202 caller of this slot observes success without executing the generic repair body. The instruction-level fact is the zero return; current RM defines `NV_OK` as `0x00000000` (`/tmp/gsp_inner_19f040_a.elf`, VAs `0x01975824..0x01975830`; `/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/nvstatuscodes.h:27`).
- **PROVED:** The generic build still enables the feature family: `RMCFG_FEATURE_LTS_REPAIR` is 1 and described as “Support for LTS swapping in-field” (`/usr/src/nvidia-610.43.03/src/nvidia/generated/rmconfig.h:340`). This compile-time flag does not override the per-chip no-op binding proved above.
- **PROVED:** A bounded replay of only the group-2 constructor decision block gives these method bindings (the replay interprets constructor instructions but does not execute firmware): index 64 -> `+0x188 = 0x0156df8c`, `+0x1b0 = 0x0156e394`; index 65/GB202 -> `+0x188 = 0x01975824`, `+0x1b0 = 0x01975874`; indices 76 and 77 -> `+0x188 = 0x0156df8c`, `+0x1b0 = 0x01581374` (`/tmp/gsp_inner_19f040_a.elf`, group-2 constructor VAs `0x0198d010..0x0198f254`; replay helper `/home/user/rt_5090_project/parallel/gsp_inforom_vtable_replay.py`).
- **PROVED:** The two substantive `+0x1b0` implementations are precisely the two enclosing functions that contain the marking-log references: function VA `0x0156e394` contains references at `0x0156e842` and `0x0156eb64`, while function VA `0x01581374` contains the reference at `0x01581dd4` (`/tmp/gsp_inner_19f040_a.elf`, bounded functions `0x0156e394..0x0156ecbe` and `0x01581374..0x01581e0e`).
- **PROVED:** GB202's selected `+0x1b0` method at VA `0x01975874` is also a 16-byte zero-return stub (`/tmp/gsp_inner_19f040_a.elf`, VAs `0x01975874..0x01975880`). Thus GB202 is not bound to either marking-log implementation.
- **PROVED:** A second bounded constructor block assigns the no-spare handler VA `0x0157b570` to object slot `+0x5e8` for every tested group-2 index, including GB202 index 65. For GB202 the path reaches the store at VA `0x01b2a26e`; companion slots are stored at `0x01b2a2aa..0x01b2a2b6` (`/tmp/gsp_inner_19f040_a.elf`, constructor entry/window `0x01b29f4c..0x01b2a2b6`; same replay helper with `--extension`).
- **PROVED:** Inside that handler, VAs `0x0157b662..0x0157b672` load the object's `+0x188` method, pass operation selector `3`, and call it indirectly. The no-spare log is on a later conditional path at `0x0157b67c..0x0157b68a` (`/tmp/gsp_inner_19f040_a.elf`, function `0x0157b570..0x0157b78a`). For GB202 this indirect call therefore resolves to the `0x01975824` zero-return stub, not the generic repair method.

## 3. Object identity and bounded caller chain

- **PROVED:** These slots belong to `OBJINFOROM`, not an unidentified generic object. The stripped class descriptor at file offset `0xc75e50`, VA `0x01c75e50`, contains object size `0x2170` and class ID `0x000e1639`; its constructor pointer at VA `0x01c75e60` is `0x0198c880`, the constructor whose slots were replayed above (`/tmp/gsp_inner_19f040_a.elf`, VAs `0x01c75e50..0x01c75e67`). Current open RM defines class ID `0x0e1639` as `OBJINFOROM` (`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_eng_desc_nvoc.h:302-307`). The constructor directly invokes its extension constructor at `0x0198ce70..0x0198ce74`, targeting `0x01b29a48` (`/tmp/gsp_inner_19f040_a.elf`, those VAs).
- **PROVED:** A small wrapper at VA `0x01062c90` is an immediate virtual-slot caller. After validating a 16-bit value `0xa8`, it calls its object argument's `+0x1a0` slot at `0x01062ce4..0x01062cec`, then loads `+0x1b0` at `0x01062cee` and calls it at `0x01062cfc` (`/tmp/gsp_inner_19f040_a.elf`, function `0x01062c90..0x01062d0c`).
- **INFERENCE:** When that wrapper's object argument is the identified `OBJINFOROM`, constructor resolution makes the second call target `0x0156e394` for index 64, `0x01581374` for indices 76/77, and the zero-return stub `0x01975874` for GB202/index 65 (`/tmp/gsp_inner_19f040_a.elf`, constructor VAs `0x0198d010..0x0198f254` and call VA `0x01062cfc`).
- **UNKNOWN:** The stripped ELF and open-source subset do not expose a source-level name for the wrapper at `0x01062c90`, prove which invocations pass `OBJINFOROM`, or expose all higher-level callers. A raw scan for `ld +0x1b0; jalr` produces many unrelated classes with the same slot offset, so treating all such sites as `OBJINFOROM` callers would be unsound (`/tmp/gsp_inner_19f040_a.elf`, executable `PT_LOAD`; helper `/home/user/rt_5090_project/parallel/gsp_l2_xrefs.py`).
- **PROVED:** There is, however, a named higher-level caller for the `+0x5e8` handler. A method descriptor at VA `0x01c1eb20` pairs function pointer `0x01066260` with method ID `0x00800102` and parameter size 4 (`/tmp/gsp_inner_19f040_a.elf`, VAs `0x01c1eb20..0x01c1eb3f`). Current headers identify `0x800102` as `NV0080_CTRL_CMD_BIF_RESET`, whose four-byte parameter is a reset `flags` word (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl0080/ctrl0080bif.h:37-65`).
- **PROVED:** In that reset-control function, the jump table for reset types 3 through 8 is at VA `0x01c43e2c`. Reset type 4 branches to `0x0106653c` and calls an object's `+0x5e8` slot with selector 4; type 5 branches to `0x0106656a` and passes selector 5; type 8 branches to `0x0106661a` and passes selector 8 (`/tmp/gsp_inner_19f040_a.elf`, VAs `0x01066506..0x0106652a`, jump-table `0x01c43e2c..0x01c43e43`, and call sites just cited). The public names of those types are respectively `BOOT_DEVICE_FUSE`, `BOOT_DEVICE`, and `BASE` (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl0080/ctrl0080bif.h:68-76`).
- **INFERENCE:** The reset function's `+0x5e8` calls target the identified `OBJINFOROM` handler `0x0157b570`: the bounded direct-xref scan finds that target installed at `+0x5e8` by the `OBJINFOROM` extension constructor, and the handler itself immediately uses other slots from the same constructor layout (`/tmp/gsp_inner_19f040_a.elf`, constructor VAs `0x01b29f4c..0x01b2a2b6`, reset call sites `0x0106653c..0x01066624`, handler `0x0157b570..0x0157b78a`). The open subset does not provide the GSP `OBJGPU` child-offset layout needed to turn this virtual-object identification into a source-name proof.
- **PROVED:** Inside the identified handler, the next edge is explicit: `0x0157b662..0x0157b672` loads its own object's `+0x188`, passes selector 3, and calls it (`/tmp/gsp_inner_19f040_a.elf`, those VAs). If the reset-side object is `OBJINFOROM`, the bounded chain is therefore `NV0080_CTRL_CMD_BIF_RESET` -> `OBJINFOROM +0x5e8` -> `OBJINFOROM +0x188`.
- **PROVED:** For a GB202 `OBJINFOROM`, that final edge resolves to `0x01975824`, so presence of the reset call sites and no-spare-log function does not make the substantive LTS-repair body active on this chip (`/tmp/gsp_inner_19f040_a.elf`, constructor VAs `0x0198da5a..0x0198da7c`, `0x0198de56..0x0198de5e`, and stub `0x01975824..0x01975830`).

## 4. Repair semantics, InfoROM update, and activation timing

- **PROVED:** This firmware family describes the feature as an in-field swap, not as a manufacturing-only flow: `RMCFG_FEATURE_LTS_REPAIR` is documented as “Support for LTS swapping in-field” (`/usr/src/nvidia-610.43.03/src/nvidia/generated/rmconfig.h:340`). The marking messages themselves say the selected LTS is marked “along with its pair for repair” and instruct the operator to perform a reset/reboot “to activate repair” (`/tmp/gsp_inner_19f040_a.elf`, strings at VAs `0x01e7ec50` and `0x01e7ed10`).
- **PROVED:** The first substantive marking method asks `OBJINFOROM +0x210` for a reset kind at `0x0156e818..0x0156e826`; return value 6 selects `bus reset` through branch target `0x0156ebe2`, value 7 selects `os reboot` at `0x0156e836`, and other values select `unknown` at `0x0156e8ba` (`/tmp/gsp_inner_19f040_a.elf`, those VAs). The second implementation likewise calls `+0x210` at `0x01581c4a..0x01581c58`; value 6 selects `bus reset` at `0x01581d70`, otherwise the shown path uses `unknown` at `0x01581c7a` (`/tmp/gsp_inner_19f040_a.elf`, those VAs).
- **PROVED:** The repair is not DRAM row remapping. The firmware keeps separate reason strings in adjacent table entries: `pending row remap`, `pending bank remap`, and `pending LTS swap` are distinct entries 1, 2, and 3 at VAs `0x01dcd7d8`, `0x01dcd7e0`, and `0x01dcd7e8` (`/tmp/gsp_inner_19f040_a.elf`, table `0x01dcd7d0..0x01dcd810`). It also has separate row-remapper activation logs at VAs `0x01e7ea68` and `0x01e7eb58`, and a bank-remapper activation log at `0x01e81998`, versus the LTS marking logs cited above (`/tmp/gsp_inner_19f040_a.elf`, those string VAs).
- **PROVED:** The supported-chip marking bodies mutate state inside the identified `OBJINFOROM`. Implementation 1 sets a GPU-side byte at offset `+0x50d9` and object byte `+0x214a` to 1 at `0x0156e98a..0x0156e998`, then loads/calls `OBJINFOROM +0x6a0` at `0x0156e99c..0x0156e9a4`. Implementation 2 sets the GPU-side byte and calls `+0x6a0` at `0x01581d12..0x01581d24`, then sets object byte `+0x214a` after a successful return at `0x01581d2a..0x01581d30` (`/tmp/gsp_inner_19f040_a.elf`, those VAs). Offset `0x214a` is within the descriptor-proved `OBJINFOROM` size `0x2170`.
- **PROVED:** For tested supported group-2 indices 64, 76, and 77, slot `+0x6a0` resolves to VA `0x0157a72c`. That method requires a pointer at offset `+0x2268` from its first (GPU) argument, passes size 4 to a helper, writes byte sequence `04 01 00 00` into the returned buffer, and passes that buffer with length 4 to a lower call at `0x0157a780..0x0157a784` (`/tmp/gsp_inner_19f040_a.elf`, function `0x0157a72c..0x0157a7f6`; extension-constructor store at `0x01b2afea`).
- **INFERENCE:** Because the enclosing class is `OBJINFOROM`, the marking bodies dirty object state and immediately issue the `+0x6a0` request, this is strong evidence of an InfoROM persistence/commit protocol. The stripped request opcode has no open definition, so the narrower proved statement is “InfoROM object state is changed and a four-byte backing-store request is issued”; successful physical nonvolatile programming cannot be proved from the static artifact alone.
- **PROVED:** GB202 is gated out of that persistence endpoint as well. Its extension constructor binds `+0x6a0 = 0x0197605c` at store VA `0x01b2b494`, whereas the tested supported indices bind `0x0157a72c`; `0x0197605c..0x01976068` is another zero-return stub (`/tmp/gsp_inner_19f040_a.elf`, those VAs; bounded extension-constructor replay).
- **INFERENCE:** For chips with substantive bindings, the combined static picture is a runtime/in-field repair request recorded in an InfoROM-managed object, followed by activation on a later bus reset or OS reboot. It is not runtime DRAM row remapping and is not shown as a manufacturing-only repair. Manufacturing may provision the spare topology originally, but the origin and one-time/replaceability rules of those spares are **UNKNOWN** (`/usr/src/nvidia-610.43.03/src/nvidia/generated/rmconfig.h:340`; `/tmp/gsp_inner_19f040_a.elf`, object descriptor `0x01c75e50..0x01c75e67`, marking/reset VAs `0x0156e818..0x0156e854`, and reason table `0x01dcd7d0..0x01dcd810`).
- **PROVED:** For GB202 specifically, the current firmware does not bind the substantive repair, marking, or apparent commit methods: `+0x188`, `+0x1b0`, and `+0x6a0` all resolve to zero-return stubs. Therefore the supported-chip lifecycle above must not be attributed to GB202 merely because its ELF contains the shared strings and outer reset handler (`/tmp/gsp_inner_19f040_a.elf`, stores `0x0198da7c`, `0x0198dbdc`, `0x01b2b494`; stubs `0x01975824..0x01975830`, `0x01975874..0x01975880`, `0x0197605c..0x01976068`).

## 5. Relationship to SKU LTS floorsweeping

- **PROVED:** There are two different software representations in the inspected artifacts: supported-chip repair processing modifies an `OBJINFOROM` record and issues an object backing-store request (section 4), while the public floorsweeping query describes enabled topology as physical/local LTC, LTS, and PAC masks. In particular, `NV2080_CTRL_FB_FS_INFO_LTS_MASK` returns a flattened physical/local `ltsEnMask` for an FBP, and `NV2080_CTRL_FB_FS_INFO_PAC_MASK` returns a physical/local `pacEnMask` (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080fb.h:2007-2033,2237-2249,2284-2300`). This proves distinct software bookkeeping/interfaces, not distinct hardware map storage.
- **INFERENCE:** The phrases “swapping in-field,” “along with its pair,” and “no more spare L2 slices” are consistent with replacing a bad active pair with a reserved pair while preserving usable capacity (`/usr/src/nvidia-610.43.03/src/nvidia/generated/rmconfig.h:340`; `/tmp/gsp_inner_19f040_a.elf`, string VAs `0x01e7ec50`, `0x01e7ed10`, `0x01e818a0`). They are not evidence that a repair operation can raise the SKU's active-LTS floor.
- **UNKNOWN:** Neither current open RM nor the bounded GSP windows expose a named LTS-spare-map structure, a dedicated repair-map register, or boot code showing how an InfoROM LTS record is combined with fuse/SKU/software floorsweep masks. The final `ltsEnMask` interface has no provenance field (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080fb.h:2021-2033`; `/tmp/gsp_inner_19f040_a.elf`, bounded repair functions and constructors cited in sections 2-4). Therefore a physically separate repair/spare map versus reuse of units represented in ordinary floorsweep state is **not demonstrated** here; separation beyond the proved InfoROM bookkeeping remains an inference.
- **UNKNOWN:** The exact code consumer and semantic type of the pointer table containing `pending LTS swap` were not recovered. The string is provably table element 3, adjacent to row/bank pending reasons, but no direct PC-relative code reference to that pointer-table base was found in the bounded executable scan (`/tmp/gsp_inner_19f040_a.elf`, table `0x01dcd7d0..0x01dcd810`; helper `/home/user/rt_5090_project/parallel/gsp_l2_xrefs.py`). It must not be promoted into a proved public status bit or a proved on-media field layout.
- **PROVED:** On GB202 there is no operative firmware repair map to compare in these methods because all three substantive inner slots are stubs. The shared no-spare text also does not prove that GB202 contains or exposes any usable LTS spare inventory (`/tmp/gsp_inner_19f040_a.elf`, stores `0x0198da7c`, `0x0198dbdc`, `0x01b2b494`; no-spare string `0x01e818a0`).

## 6. Non-invasive observability exposed by current open RM

- **PROVED:** Open RM declares a read/query surface for active topology. `NV2080_CTRL_CMD_FB_GET_FS_INFO` supports query type `NV2080_CTRL_FB_FS_INFO_LTS_MASK` (`0x3`) and `NV2080_CTRL_FB_FS_INFO_PAC_MASK` (`0xe`), returning the masks described above (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080fb.h:2021-2033,2237-2249,2284-2300,2305-2341,2343-2359`). Its generated dispatch entry has method ID `0x20801346`, flags `0x10248`, and access right 0 (`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_subdevice_nvoc.c:10201-10213`). Flags `0x8`, `0x40`, `0x200`, and `0x10000` mean non-privileged, route-to-physical, route-to-vGPU-host, and GSP-plugin-for-vGPU-GSP respectively (`/usr/src/nvidia-610.43.03/src/nvidia/inc/kernel/rmapi/control.h:201-205,226-230,246-250,282-287`).
- **PROVED:** A second exported control, `NV2080_CTRL_CMD_FB_GET_LTC_INFO_FOR_FBP`, reports the active LTC and LTS masks/counts for a physical FBP (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080fb.h:1239-1269`); its dispatch entry is method `0x20801328` (`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_subdevice_nvoc.c:9991-10004`). The generic FB-info path also exposes an aggregate active LTS count through `NV2080_CTRL_FB_INFO_INDEX_LTS_COUNT` (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080fb.h:263-270,356-358`; `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/mem_sys/kern_mem_sys_ctrl.c:91-100`).
- **INFERENCE:** If supported by the running target, those query controls can observe the currently reported active/effective topology. They cannot identify why an LTS is disabled, whether an enabled LTS is an original or swapped-in unit, how many spares remain, or whether an InfoROM LTS swap is pending, because their output structures contain only masks/counts and per-query status (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080fb.h:2007-2033,2237-2249,2305-2330`). No control was invoked in this audit.
- **PROVED:** Open RM's nominal repair-status control does **not** cover LTS. `NV2080_CTRL_CMD_ECC_GET_REPAIR_STATUS` is documented only for TPC/Channel repair and returns exactly `bTpcRepairPending` and `bChannelRepairPending` (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080ecc.h:202-220`). Its generated method is present with non-privileged/route-to-physical flags `0x48` (`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_subdevice_nvoc.c:12991-13004`; flag definitions above).
- **PROVED:** ECC counters provide health context, not repair-map state. The client-exposed counter structure includes an aggregate `sramBucketL2`, while volatile counts are aggregate SRAM/DRAM counts (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080ecc.h:40-82,84-110`); both have exported `0x48` dispatch entries (`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_subdevice_nvoc.c:12931-12959`). They do not identify a slice, spare, swap, or pending LTS repair.

### Plain-language summary

The current GSP contains real L2-slice repair machinery for some chip indices, but GB202 is wired to success stubs at every substantive inner step (`/tmp/gsp_inner_19f040_a.elf`, constructor stores `0x0198da7c`, `0x0198dbdc`, `0x01b2b494`). On chips that do use it, the code stages an LTS-pair swap in an InfoROM-managed path and tells the system to reset or reboot before activation; it is not DRAM row remapping and does not look like a factory-only operation (`/usr/src/nvidia-610.43.03/src/nvidia/generated/rmconfig.h:340`; `/tmp/gsp_inner_19f040_a.elf`, marking strings `0x01e7ec50`, `0x01e7ed10`). Static evidence proves separate repair bookkeeping, but not a hardware spare map independent of ordinary SKU floorsweeping (`/tmp/gsp_inner_19f040_a.elf`, `OBJINFOROM` descriptor `0x01c75e50..0x01c75e67`; `/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080fb.h:2007-2033`). Open RM can report the active LTS topology and coarse L2 health, but not a pending GB202 LTS swap, spare count, repair provenance, or repair-record contents (`/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080fb.h:1239-1269,2007-2033`; `/usr/src/nvidia-610.43.03/src/common/sdk/nvidia/inc/ctrl/ctrl2080/ctrl2080ecc.h:40-110,202-220`).
