## 2. Container and payload boundaries

### 2.1 MODS: removable archive layers lead to a host producer

- **FACT:** The outer deflate/BZip2/gzip layers are conventional package layers and the extracted host ELF is available byte-for-byte (`mods_audit/static_audit.md:24-45`). They do not prevent inspection of the task-2 sender.
- **FACT:** A bounded x86-64 window shows the host call explicitly loads task `2` in `esi`, subobject `1` in `edx`, null response-vector in `r8d`, and calls `0x185e890` (`mods_audit/static/extracted_inner/mods` @ text VAs `0x106c570..0x106c58c`). This is the producer/sender, not code executing inside FSP.
- **FACT:** MODS also has 72 proprietary `.jse` leaf files. All begin with common bytes `f1 1a 80` at file offset `0x0`; representative first 16 bytes are `f1 1a 80 9a 49 08 00 00 00 00 00 33 5f dc da f0` in `mods_audit/static/extracted_inner/gputest.jse` and `f1 1a 80 89 45 00 00 00 00 00 00 33 5f dc da f0` in `mods_audit/static/extracted_inner/thermcal.jse` (each @ `0x0..0xf`). Their representative near-maximal entropy and lack of useful long strings are recorded at `mods_audit/static_audit.md:81-92`.
- **UNKNOWN:** Local evidence does not define the JSE header length or distinguish encryption from compression/another encoding, so no inner JSE payload offset can be assigned. The conservative boundary is therefore the proprietary file format beginning at offset `0x0`, not a guessed cipher boundary. **INFERENCE:** These are host test-script assets, not affirmative evidence of a production device-side FSP handler; nevertheless, literal duplicated bytes inside their undecoded bodies cannot be ruled out.

- **FACT:** The installed outer ELF has `.fwimage` at file `[0x40,0x5053040)`, `.fwversion` at `0x5053064` containing `610.43.03`, and a GB20x signature section `.fwsignature_gb20x` at `[0x505706e,0x505806e)` (`/usr/lib/firmware/nvidia/610.43.03/gsp_ga10x.bin` @ ELF section table file offset `0x505f3d8`).
- **FACT:** A second RISC-V executable ELF header begins at outer file offset `0x19f040`; the current `/tmp/gsp_inner_19f040_a.elf` is byte-identical to the outer suffix there (`parallel/GSP_ARTIFACT_PROVENANCE.md:14-42`; direct headers at outer `0x19f040` and inner `0x0`). Its executable and writable load segments are `[file 0x0,0xe97000)` at VA `0x01000000` and `[file 0xe97000,0x106c000)` at VA `0x04000000` (`/tmp/gsp_inner_19f040_a.elf` @ ELF program-header table offset `0x40`).
- **FACT:** The inner executable is stripped; its bounded string scan produced no `task2`, `task 2`, `subobject1`, `subobject 1`, `FSP_RUN`, or MODS floorsweeping diagnostic hit (`/tmp/gsp_inner_19f040_a.elf` @ whole-file string coverage). This is only a literal-string negative.

## 3. Search for a production task-2/subobject-1 consumer

### 3.1 What is present

- **FACT:** A MODS **producer** is present. The bounded host disassembly supplies task `2`, subobject `1`, payload pointer, and null response vector at `mods_audit/static/extracted_inner/mods` text VAs `0x106c570..0x106c58c`. The common sender then enters a transport response-completion callback before returning status (`mods_audit/static/extracted_inner/mods` @ text VAs `0x185e890..0x185e8ed`; detailed vtable closure at `parallel/task2_lifecycle_audit.md:132-183`).
- **FACT:** Current OpenRM contains the FSP host endpoint, generic message transport, and generic three-word response schema—not the device handler. The schema is only `taskId`, `commandNvdmType`, `errorCode` (`/usr/src/nvidia-610.43.03/src/nvidia/arch/nvalloc/common/inc/fsp/nvdm_payload_cmd_response.h:35-42`). A bounded exact search across the 13 files under `src/kernel/gpu/fsp`, `inc/kernel/gpu/fsp`, and `arch/nvalloc/common/inc/fsp`, plus all seven GB202 bindata C files, found zero `task2`, `task 2`, `subobject1`, `subobject 1`, `0x8200d0`, `0x8200dc`, or `0x8200f8` hits (named source directories @ whole-file exact-pattern coverage).
- **FACT:** GB202's public FSP HAL contains no host-visible FSP image loader; it states that Bootfsm triggers FSP execution out of chip reset and the host polls a boot-complete scratch value (`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/blackwell/kern_fsp_gb202.c:50-85`). **INFERENCE:** This is consistent with the absence of a standalone `fsp_*.bin` from the inventoried 610 directory; it does not identify the underlying code source.

- **FACT:** `mods` is x86-64 host code and the observed task-2 block is the sender (`mods_audit/static/extracted_inner/mods` @ ELF header `0x0`, text VAs `0x106c570..0x106c58c`).
- **FACT:** `gsp_ga10x.bin`, its inner RISC-V ELF, and the GB202 FMC/GFW bindata are GSP-RM/GSP-FMC boot material selected and booted through FSP, not the already-running FSP runtime (`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/arch/hopper/kernel_gsp_gh100.c:779-899`; `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:784-821`).

### 3.3 Presence verdict

- **FACT (carefully scoped negative):** Within the stated header/symbol/string/small-window coverage, no inspectable plaintext or symbolized local artifact exposes an identifiable production GB202 task-2/subobject-1 dispatch table or handler. This covers the MODS host sender windows, the GB20X `gsp_ga10x.bin` headers/sections/symbols/strings, the zero-body `ucodes` files, the 13 public FSP host files, all seven GB202 generated-bindata metadata files, the readable HPE MCU component plus signed footer, and the three unique bounded VBIOS target regions at the locators above.
- **UNKNOWN:** Literal byte-presence of the production consumer in “any file” cannot be decided. The consumer may be plaintext only after authenticated processing of one of the encrypted-flag v6 `app=0x24,target=0x0f` objects; it may instead reside in chip ROM or another device-internal image that is not saved locally. The 72 proprietary JSE bodies also prevent an absolute all-local-byte negative, although their evidenced role is host test logic rather than FSP runtime (`mods_audit/static_audit.md:81-92`). A failed literal search cannot distinguish these cases.
- **INFERENCE:** The VBIOS `FSP_RUN` objects are the strongest local carrier candidates because their Falcon descriptors are explicitly encrypted and GB202 FSP starts through Bootfsm after reset (`vbios_diff/unverified_TPU_276859_RTX5090_FE_98.02.2E.00.03.rom` @ descriptor `0x11b304`; `vbios_diff/dell_8d_payload/RTXPRO6000_GB202_GPU_98.02.8D.00.01.nvfw` @ `0x128104`; `vbios_diff/hpe_scexe_payload/RTXPRO6000_GB202_GPU_98.02.9E.00.01.nvfw` @ `0x12cd04`; `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/blackwell/kern_fsp_gb202.c:50-61`). No local source maps `app=0x24,target=0x0f` or the `FSP_RUN` printable bytes to task 2/subobject 1, so this cannot be upgraded to presence.
- **UNKNOWN:** The exact division of FSP functionality between immutable chip ROM, the v6 VBIOS object, and any authenticated device-internal expansion stage is not documented by the inspected files. “Bootfsm triggers FSP” is not proof that the full runtime consumer is ROM-resident.

## 4. Conclusion

### Exact boundary statement

1. **FACT:** ZIP/TBZ/TGZ, RPM/scexe/fwpkg, raw-DEFLATE bindata, and GSP ELF section nesting are all statically traversable at the cited offsets/lines; none is the inspection blocker. The HPE package's post-NVFW bytes split into readable MCXN236-compatible PLDM component 1 and a separately authenticated `0x400` footer, not one undifferentiated encrypted trailer.
2. **FACT:** The inventoried MODS package, installed `610.43.03` firmware directory, VBIOS/update set, and GB202 generated bindata expose no standalone FSP firmware file. OpenRM starts by waiting for Bootfsm-started FSP, while the local GSP/FMC blobs are explicitly material that FSP later boots (`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/blackwell/kern_fsp_gb202.c:50-85`; `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/arch/hopper/kernel_gsp_gh100.c:779-899`).
3. **FACT:** The closest local FSP-domain candidates are the three unique VBIOS Falcon v6 objects. Public parsing reaches each entry and its four-byte descriptor word, where `flags.bit2=1` declares encrypted; public 610 has no v6 body definition (`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/kernel_gsp_fwsec.c:100-188,627-669`; exact sample offsets in section 2.4).
4. **INFERENCE:** The likely stored-object regions are the three `[start,end)` slices in section 2.4, based on the v2/v3 `StoredSize` position and consistent `0xff` end transitions. This identifies a precise practical byte boundary without pretending the v6 private word is publicly defined.
5. **UNKNOWN:** Whether any encrypted v6 object actually contains the production task-2/subobject-1 consumer, whether it is compressed internally, or whether the consumer is only in chip-internal/unsaved code remains unresolved. The undecoded MODS JSE bodies independently prevent a literal all-local-byte absence claim, but nothing inspected identifies them as a device consumer. No evidence found contradicts the main report's narrower wording “no readable GB202 consumer” (`L2_REENABLE_STATIC_FINDINGS.md:365-375,1175-1180`); the stronger wording “the consumer is absent from every local file” would be unsupported.

Plain-language summary: the sender is in MODS, but the receiver is not available as identifiable readable code. The normal archives, DEFLATE data, GSP ELF, HPE's separate MCXN236 management-firmware component, and its signed-package footer can all be inspected. MODS's proprietary JSE test scripts remain opaque at the file-format boundary, but no evidence makes them the device receiver. The meaningful device-code stop is the Blackwell Falcon v6 object in the saved VBIOS images: raw bit 2 is set and the older common header names it encrypted, while the private v6 format is not published. It may contain the receiver, but the current files cannot prove that. The other possibility is code supplied inside the chip or another unsaved authenticated stage. Nothing was run and no GPU was touched.
