# GB202 MODS permission and sequencing audit

Status: complete (bounded static analysis only)

## Scope and evidence labels

This audit examines the locally extracted MODS executable without running it. It uses only bounded `readelf`, `strings`, `rg`, and small address-window disassembly reads. No live GPU, `/dev/nvidia*`, PCI/BAR/MMIO, debugfs, RM control, reset, rebind, module, firmware, clock, power, or system-configuration operation was performed.

- **PROVED** means the stated control flow/data relationship is directly visible in the cited local artifact.
- **INFERENCE** means the cited facts support the interpretation, but the interpretation is not itself directly encoded.
- **UNKNOWN** means the inspected bounded evidence does not decide the question; a failed search is not treated as proof of impossibility.

## Artifact and address basis

- **PROVED:** The inspected artifact is the stripped x86-64 ELF `mods_audit/static/extracted_inner/mods`, SHA-256 `c30461e21dfcd8a27687481f9618206d4291c0b3e24f039d270dec944c06c7bf`. Its `.text` is VA `0x4a0940`, file offset `0x0a0940`, size `0x8736b3a`; because VA and file offset differ by `0x400000`, a cited text VA `V` maps to file offset `V-0x400000` (`mods_audit/static/extracted_inner/mods`, ELF section header table at file offset `0x176296a0`, `.text` section entry).

## Findings

### 1. Host policy gate and local writer sequence

- **PROVED:** The gate at the start of `ProgramSwFusePlan` is process-local MODS policy, not a GPU/FSP decision. At `0x1515eb4` the function calls trampoline `0xd53530`, which jumps to `0xd5d660`; that getter only loads the process global dword at `0x186d6f74`. `0x1515eb9..0x1515ed1` returns error `3` unless the value is greater than `3`, before the first GPU-object call at `0x1515ed8` (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515eb4..0x1515ed8`, `0xd53530`, `0xd5d660`).
- **PROVED:** Values `4` and `5` are named `SUL_NVIDIA_NETWORK` and `SUL_NVIDIA_NETWORK_BYPASS` in the sample; the names are at file offsets `0x8cc823d` and `0x8cc8223` (VAs `0x90c823d` and `0x90c8223`). The setter at `0xd5d5d0` writes the same process global and includes the host network-test branch at `0xd5d610..0xd5d631`; it does not accept a GPU result. Thus the numeric `>3` test is a host authentication/policy gate even though legitimate acquisition of those levels may depend on NVIDIA network/bypass material (`mods_audit/static/extracted_inner/mods`, file offsets `0x8cc8223..0x8cc8278`; text VAs `0xd5d5d0..0xd5d666`).
- **PROVED:** `SetSwFusesCore` constructs/prepares its host plan before dispatching it: the ordinary branch calls preparation helper `0x147b4b0` at `0x1462194`, then calls programming dispatcher `0x1458a80` at `0x14621f3`. The `level > 3` check is therefore the start of device-plan application inside `ProgramSwFusePlan`, not the start of all host-side encoding work (`mods_audit/static/extracted_inner/mods`, text VAs `0x1462194..0x14621f8`, `0x1515ea0..0x1515ed8`; `L2_REENABLE_STATIC_FINDINGS.md:421-440`).
- **PROVED:** After the host gate passes, the first writer action is a virtual call `DeviceFuseAccessHandler +0x78` with RegHal constant `0x404f0001` at `0x1515ed8..0x1515eea`. The caller neither tests nor stores the return before moving into the plan machinery at `0x1515eed`; whatever the device does with the request, this host routine does not fail closed on its result (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515ed8..0x1515f1d`).
- **INFERENCE (strong):** RegHal reconstruction maps `0x404f0001` to `0x820040.bit0=1`, and the paired resense path later uses `0x404f0000`; together these support calling the first request an attempted software-override latch set. The meaning is reconstructed rather than named by the machine instruction itself (`L2_REENABLE_STATIC_FINDINGS.md:435-440`; `mods_audit/static/extracted_inner/mods`, text VAs `0x1516e41..0x1516e55`).
- **PROVED:** Runtime order inside each plan iteration is raw write then raw readback, followed by an ordinary-value comparison. The write side loads the plan offset/value at `0x1516018..0x151602a` and calls handler slot `+0xb8` at `0x151606b`; control then reaches the read side, which calls slot `+0xc0` at `0x1515fb3` and normally compares the returned dword with `[node+0x24]` at `0x1515fc1..0x1515fc6`. Handler thunks `0x151ad00` and `0x151ad10` forward those slots to `GB202GpuSubdevice +0x238` and `+0x228`, respectively (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515f50..0x15160a7`, `0x151ad00..0x151ad1d`).
- **PROVED:** The host routine does not examine a status result from the raw-write call at `0x151606b`; the next instruction starts the pacing/iteration machinery, and control later reaches readback. Consequently, its host-visible detection of a rejected/ineffective raw write rests on the subsequent read result rather than a checked write acknowledgement (`mods_audit/static/extracted_inner/mods`, text VAs `0x1516066..0x151607d`, `0x1515f5a..0x1515fc6`).
- **PROVED:** Readback is not uniformly fail-closed. If the read returns special value `0xbadf510c`, `0x1515fb6..0x1515fbb` branches to the log `Priv-level violation while verifying offset [0x%08x] on D%u`, then `0x15160a7` advances to the next node without changing the aggregate status at `[rsp+0xc]`. That actual string is at VA `0x8c526e0`, file offset `0x88526e0`; the unrelated `Unexpected true read mismatch ...` string is at file offset `0x8852ac0` and is not selected here (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515fb6..0x1515fbb`, `0x1516090..0x15160a7`; string file offsets just cited). An ordinary unequal dword, by contrast, records `0x79`.
- **PROVED:** An ordinary unequal readback records `0x79` only if no earlier error is present (`0x1515fe3..0x1515ff1`), then advances to the next red-black-tree node (`0x1515ff5..0x1516004`). It does not abort the remaining plan. This directly proves that a multi-register plan is not host-transactional (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515fc1..0x151600a`).
- **PROVED:** `ProgramSwFusePlan` contains no call to the separate `IsSwFusingAllowed` helper and no `DeviceFuseAccessHandler +0xb0` access precheck in its bounded body `0x1515ea0..0x15160df`. Consequently, `0x8212ac.bit0` is proved to gate the separate soft-burn query path, but its effect on this direct-shadow path is **UNKNOWN** and would have to arise below this host routine; this agrees with the correction in `parallel/evidence_audit.md:203-209` (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515ea0..0x15160df`; `parallel/evidence_audit.md:203-209`).

### 2. Failure and success tails

- **PROVED:** In the ordinary core branch, the programming dispatcher called at `0x14621f3` returns a status; a nonzero status branches at `0x14621fa` directly to cleanup `0x146219d`. That cleanup calls `0x1457470` twice and returns, while the successful branch alone calls vtable `+0x370` at `0x146223c`. The second core branch likewise calls `+0x370` at `0x14623f9` only after its programming helper succeeds (`mods_audit/static/extracted_inner/mods`, text VAs `0x1462194..0x146224f`, `0x14623ca..0x1462403`).
- **PROVED:** Pre-program preparation failures are distinguishable from writer failures. An error from `0x147b4b0` at `0x1462194..0x146219b` enters cleanup before the `0x14621f3` dispatcher, and the alternate branch similarly checks `0x1471170` at `0x1462388..0x146239b` before calling its programming dispatcher at `0x14623da`. The partial-latch/raw risk begins only once a programming dispatcher has entered the writer; it must not be attributed to a preparation-only error (`mods_audit/static/extracted_inner/mods`, text VAs `0x1462194..0x14621f3`, `0x1462376..0x14623e3`).
- **PROVED:** Cleanup helper `0x1457470` recursively destroys plan nodes and frees their allocations; its bounded body has allocator/destructor calls but no GPU/device argument, RegHal constant, raw-register write, latch clear, or reset call (`mods_audit/static/extracted_inner/mods`, text VAs `0x1457470..0x145750c`). Therefore the inspected host failure path has no rollback of already written raw items, no latch clear, and no reset/reinit.
- **UNKNOWN:** The preceding fact proves absence only from the inspected MODS host failure path. It does not prove that inaccessible GPU/FSP internals could never reject atomically, restore state, or clear state on some later transition. No such behavior is evidenced by the immediate readback loop, and no current artifact here proves it (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515fc1..0x151600a`, `0x146219d..0x146224f`; `parallel/evidence_audit.md:347-350`).
- **PROVED:** The success callback chain is `SetSwFusesCore +0x370` (`0x146223c` or `0x14623f9`) -> MultiMacro `0x146dd30` -> each accessor `+0x90` at `0x146dd62` -> GB20x implementation `0x1515770` -> handler `+0x100` -> thunk `0x151ad50` -> `GpuSubdevice +0x1b0` -> GB202 implementation `0x127b000` -> `0xdff7b0` -> RM-state dispatcher `0xdfe3d0` (`mods_audit/static/extracted_inner/mods`, text VAs `0x146223c`, `0x14623f9`, `0x146dd30..0x146dd80`, `0x1515770..0x1515786`, `0x151ad50..0x151ad5d`, `0x127b000..0x127b074`, `0xdff7b0..0xdff831`).
- **PROVED:** The integer `5` loaded by `0x1515777` is not the final reset selection: `0x151ad50` discards it when it jumps through the one-argument `+0x1b0` method, and `0xdff7b0` creates request value `2` before invoking GB202 mapper `+0x1070`. For request `2`, mapper `0x126b360` reads boot/fuse/base coupling constants and selects base state `7`, else fuse `6`, else boot `5`, else hot `3`; its jump-table entry for request `2` is `0x126b430`, and it writes descriptor byte `+8 = 0` (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515770..0x1515786`, `0x151ad50..0x151ad5d`, `0xdff7b8..0xdff7d4`, `0x126b374..0x126b4a6`; jump table VA `0x92c0900..0x92c093f`).
- **PROVED:** `0x127b000` performs one normal reset/reinit call first. Only after that call returns success does it test recovery-mode property `0x42384201` at `0x127b020..0x127b04f`; a true result triggers a second `0xdff7b0` call at `0x127b062..0x127b06f`. Thus a second reset is recovery handling, not a two-phase commit (`mods_audit/static/extracted_inner/mods`, text VAs `0x127b000..0x127b074`).
- **PROVED:** Because the special `0xbadf510c` readback path does not set an error, the upper core can still take its success/reset path if no other node fails. A MODS success status therefore proves neither a checked latch result nor an ordinary equality comparison for every plan node (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515fb6..0x1515fbb`, `0x1516090..0x15160a7`, `0x14621f3..0x146224f`).

### 3. Device-side permission evidence versus host policy

- **PROVED:** The GB20x floorsweep path in this MODS sample constructs a payload, then calls the common sender with `task=2`, `subobject=1` at `0x106c570..0x106c58c`. The sender's task-2 case checks a capability at `0x185e530..0x185e55c` and returns `0x12d` if it is unavailable. This is a real FSP/capability-mediated operation, not the process-global security-level test (`mods_audit/static/extracted_inner/mods`, text VAs `0x106c4e0..0x106c5bc`, `0x185e530..0x185e55c`).
- **PROVED (ID corrected):** MODS also has an optional FSP PRC knob transaction before floorsweeping. The complete 0x28-byte record reconstruction identifies knob `0x1d` as `PRC_KNOB_ID_FLOORSWEEPING_ALLOW_INB_ONE_SHOT`; `0x1c` is the preceding `RPR_ALLOW_INB` record. Executor `0x185ef60` first reads each requested knob (`0x185f336..0x185f37b`), sends task `13`/submessage `2` only when the value differs (`0x185f1c0..0x185f29e`), then reads back and compares (`0x185f2a6..0x185f2ee`). A post-write mismatch logs and returns `0x12f` at `0x185f458..0x185f474`. This executor has no call to the `0xd53530` security-level getter; acceptance is determined by the FSP response/readback (`mods_audit/static/extracted_inner/mods`, text VAs `0x185ef60..0x185f4b8`; corrected record proof in `parallel/prc_knob_metadata.md`).
- **INFERENCE:** The name and placement of PRC knob `0x1d` support interpreting it as an FSP-controlled allow-inband/one-shot permission preparation, but neither a required value nor its self-clear/consumption point is proved. It must not be treated as a host boolean that grants itself (`parallel/prc_knob_metadata.md`).
- **PROVED (host ordering only):** When ordinary and `*_ALLOW_INB` PRC knobs are submitted together, the decoded callback first loses input order by storing them in a name-keyed map; executor `0x185ef60` then orders ordinary knobs before `ALLOW_INB` knobs. A single batch therefore cannot be assumed to perform “grant allow-inband first, then perform the protected action,” regardless of command-line order (`mods_audit/static/extracted_inner/mods`, text VAs `0x116bd50..0x116c0fb`, `0x185ef60..0x185f39e`; `L2_REENABLE_STATIC_FINDINGS.md:1295-1317`). Whether this reflects pre-provisioned permission or some other FSP policy is **UNKNOWN**.
- **PROVED:** In the generic floorsweep dispatcher, the virtual `+0x520` operation is called at `0x10960cc`; only after it returns success can pending host floorsweep apply run through `+0x308` at `0x109622b`. The GB20x implementation tests `doFsp` at `0x106c4f1` and sends task 2/subobject 1 only when that boolean is true. Thus, when an FSP send occurs, the proved host-visible order is task 2 first and host register apply second; `doFsp=false` is a no-send path (`mods_audit/static/extracted_inner/mods`, text VAs `0x10960a8..0x10960da`, `0x10961f9..0x1096243`, `0x106c4e0..0x106c58c`).
- **PROVED:** The Hopper-class sibling at `0x1094990` explicitly tests two RegHal fields (`0x40e0c000` and `0x4059c000`) before deciding whether to skip the same task-2/subobject-1 message; project RegHal reconstruction maps those fields to the OPT/FS and L2 PLMs at `0x8200d0` and `0x8200dc` (`mods_audit/static/extracted_inner/mods`, text VAs `0x1094a50..0x1094ae9`; `L2_REENABLE_STATIC_FINDINGS.md:1418-1424`).
- **INFERENCE (strong, not direct GB202 firmware proof):** GB202 task 2/subobject 1 is intended to make at least `0x8200d0/0x8200dc` writable long enough for the following host floorsweep apply. The supporting facts are the GB202 send-before-apply order, Hopper's same-task PLM precheck, and the L2 raw/SW access metadata pointing to `0x8200dc`; the FSP consumer is not present in inspectable host code. The independent evidence audit reaches the same classification (`parallel/evidence_audit.md:184-201`; `parallel/gb202_610_arch.md:271-277`).
- **PROVED:** RegHal access metadata distinguishes the raw-L2 and latch protections: raw/SW L2 IDs point to access offset `0xdc` (`0x8200dc`), whereas latch ID `0x104f0000` points to access offset `0xf8` (`0x8200f8`) (`L2_REENABLE_STATIC_FINDINGS.md:673-691`, `L2_REENABLE_STATIC_FINDINGS.md:747-754`). These are static address/field relationships; they do not reveal current values.
- **UNKNOWN:** No inspected GB202-specific consumer proves that task 2 lowers `0x8200f8`, that a successful task response leaves `0x8200dc` open until a later script callback, that either permission survives reset, or that firmware performs an automatic restore. The current open-source audit explicitly found no task-2 consumer or PLM lowering/restore point (`parallel/evidence_audit.md:184-201`; `parallel/gb202_610_arch.md:265-277`).
- **INFERENCE:** Because the raw plan is dispatched through `GB202GpuSubdevice` register methods and the target/latch IDs have PLM metadata, a GPU-side PRI/PLM component can independently accept, ignore, or reject the writes after the MODS host gate passes. This is why bypassing the process global would not establish write permission. Actual acceptance on this card is **UNKNOWN** (`mods_audit/static/extracted_inner/mods`, text VAs `0x151ad00..0x151ad1d`; `L2_REENABLE_STATIC_FINDINGS.md:659-699`, `L2_REENABLE_STATIC_FINDINGS.md:701-717`).
- **PROVED (routing only):** Current 610 project evidence binds GB202 `NVDM_TYPE_HULK (0x11)` transport to FSP SEID 0, while the relevant GB202 SEC2 packet/NVDM methods are stubs. It does not expose the HULK payload, task/subobject routing, or PLM action (`parallel/gb202_610_arch.md:101-123`, `parallel/gb202_610_arch.md:255-266`).
- **INFERENCE:** HULK is a device/FSP authorization path distinct from MODS's process-global level `4/5` check; neither observed mechanism proves that the other has succeeded or can substitute for it (`parallel/evidence_audit.md:211-217`; `mods_audit/static/extracted_inner/mods`, text VAs `0xd5d5d0..0xd5d666`).
- **UNKNOWN (not independently replayed here):** The MODS HULK interface/sender strings are direct sample evidence, but the main document's detailed claims about signature size, device-bound validation, and sender control flow are report-level findings in the independent evidence audit. The public 610 route alone cannot prove those FSP-internal validation rules or that HULK opens the L2 writer (`L2_REENABLE_STATIC_FINDINGS.md:830-871`, `L2_REENABLE_STATIC_FINDINGS.md:873-924`; `parallel/evidence_audit.md:211-217`; `parallel/gb202_610_arch.md:111-123`).

### 4. Exact host-visible sequence, with the permission-lifetime caveat

1. **PROVED:** MODS establishes its process-global security level through the host setter/getter at `0xd5d5d0/0xd5d660`; this is independent of the later GPU calls (`mods_audit/static/extracted_inner/mods`, text VAs `0xd5d5d0..0xd5d666`).
2. **PROVED (successful normal path):** During GB202 initialization, optional PRC read/write calls occur at `0xda39d2/0xda39f8` (so a requested knob `0x1d` is read/conditionally written/read back here), floorsweep argument processing follows at `0xda3b80`, and—when the normal FSP-enabled path actually sends task 2—the send precedes any pending host apply (`mods_audit/static/extracted_inner/mods`, text VAs `0xda39ba..0xda3bb9`, `0x185ef60..0x185f39e`, `0x10960a8..0x1096243`; call identities summarized in the main report). The qualified host-visible order is optional PRC one-shot -> optional FSP task 2/subobject 1 -> optional host floorsweep apply -> optional post-FS reset.
3. **PROVED (host control flow, qualified):** A newly constructed floorsweep object initializes pending/initialized bytes to zero at `0x109a485`. On the normal GB202 FSP-enabled path with `SkipFspFs=0` and successful prerequisites, an initial no-argument pass sends task 2 but skips host apply and the outer post-FS reset. `GB20xFs+0x520` first tests `doFsp` at `0x106c4f1`; `doFsp=false` takes the no-send branch, so the send is not unconditional across all configurations (`mods_audit/static/extracted_inner/mods`, text VAs `0x109a470..0x109a48f`, `0x106c4e0..0x106c58c`; main-report normal/skip path analysis). **UNKNOWN:** Whether FSP keeps `d0/dc` lowered until later script execution is not encoded by this host sequence.
4. **PROVED:** After the later `SetSwFuses` call has constructed its host plan, device-plan application in `ProgramSwFusePlan` first enforces `level > 3`, then attempts `0x404f0001`, then performs each raw write and immediate readback. Ordinary mismatch records `0x79`; special return `0xbadf510c` only logs and advances. Only after all plan nodes are visited does the aggregate status return (`mods_audit/static/extracted_inner/mods`, text VAs `0x1462194..0x14621f3`, `0x1515eb4..0x15160d0`).
5. **PROVED:** On any nonzero programming status, core cleanup returns without post-program reset; on success, both actual core branches unconditionally enter `+0x370`, which reaches the coupling-selected reset/reinit chain (`mods_audit/static/extracted_inner/mods`, text VAs `0x14621f3..0x146224f`, `0x14623ca..0x1462403`).
6. **UNKNOWN:** Host ordering does not prove that permission lowering happened, persisted, covered the latch, or was consumed/restored at a particular write. Those state transitions are inside FSP/PLM/hardware and no live readback or firmware consumer is available (`parallel/evidence_audit.md:184-201`; `parallel/gb202_610_arch.md:271-277`).

### 5. Rollback, latch-clear, and no-reset paths

- **PROVED:** Current GB20x code contains a paired clear-coded operation, so a blanket claim that no current path issues the clear constant is contradicted. `GB20xPrepareResense` first calls handler `+0xf8` with state `6` at `0x1516e24..0x1516e38`, then calls handler `+0x78` with `0x404f0000` at `0x1516e41..0x1516e55`. After preparation returns zero, its caller invokes handler `+0x100` only on the non-pre-silicon branch at `0x1516f5a..0x1516f6f`; the predicate-true branch logs `Skipping fuse reset on Pre Silicon Platforms!` at `0x1516f80` and returns without requesting reset (`mods_audit/static/extracted_inner/mods`, text VAs `0x1516e20..0x1516f91`; log VA `0x8c52990`).
- **INFERENCE (strong):** RegHal decoding and the paired `0x404f0001` writer operation identify the intended nominal sequence as “attempt fuse-reset coupling, clear the software-override latch, then resense/reinitialize from physical fuse state,” not rollback/commit of the new shadow plan. The distinction between accessor vtable slots `+0x88` (resense) and `+0x90` (normal post-program) supports it (`L2_REENABLE_STATIC_FINDINGS.md:1068-1077`, `L2_REENABLE_STATIC_FINDINGS.md:1158-1164`; `mods_audit/static/extracted_inner/mods`, text VAs `0x1515ed8..0x1515eea`, `0x1516e20..0x1516f91`).
- **PROVED:** Resense does not fail closed on either preparatory request. A nonzero `+0xf8` coupling result at `0x1516e39` logs `Can't couple resets for resensing` at `0x1516f10..0x1516f21`, then jumps back to the `0x404f0000` operation; the clear operation's return at `0x1516e53` is immediately overwritten. If preparation returns zero **and** the later platform predicate is false, the caller reaches reset callback `+0x100`; the pre-silicon predicate-true branch skips it (`mods_audit/static/extracted_inner/mods`, text VAs `0x1516e24..0x1516e68`, `0x1516f10..0x1516f21`, `0x1516f3e..0x1516f91`; log string VAs `0x8c52968`, `0x8c52990`).
- **PROVED:** The state-`6` argument passed to that `+0x100` callback is discarded by thunk `0x151ad50`, exactly as on the normal post-program path. The later GB202 mapper chooses base `7`, fuse `6`, boot `5`, or hot `3` from the coupling bits. Therefore a requested reset selects type `6` only when the mapper observes base=false and fuse=true; the fuse bit may have been established by this attempt or may have pre-existed, so its origin is **UNKNOWN** (`mods_audit/static/extracted_inner/mods`, text VAs `0x1516f5a..0x1516f6f`, `0x151ad50..0x151ad5d`, `0xdff7b8..0xdff7d4`, `0x126b374..0x126b4a6`).
- **PROVED:** The normal success path does not call `GB20xPrepareResense` and does not issue `0x404f0000`; the failure cleanup does neither as well (`mods_audit/static/extracted_inner/mods`, text VAs `0x146219d..0x146224f`, `0x1457470..0x145750c`, `0x1515ea0..0x15160df`). Hence the latch-clear code is not a failure rollback.
- **PROVED:** No successful no-reset variant exists in the two inspected `SetSwFusesCore` programming branches: both call `+0x370` after success without reading a reset-policy argument (`mods_audit/static/extracted_inner/mods`, text VAs `0x14621f3..0x146224f`, `0x14623ca..0x1462403`). This is a statement about the known `SetSwFuses` entry, not a claim that no other firmware mechanism can exist.
- **PROVED:** A no-reset *error tail* does exist: programming error skips `+0x370`. It is unsafe as a feature because earlier latch/raw writes may already have occurred (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515ed8..0x151600a`, `0x14621f3..0x14621b9`).
- **PROVED:** A separate initialization-level no-reset control exists: decoded argument `skip_prc_reset` maps to `Gpu.SkipPrcReset`, and setter `0xd9b020` stores byte `Gpu+0x8e`; `Gpu::Initialize` tests its global at `0xda3ca3` before the optional `+0x3c8` post-FS reset at `0xda3cba`. This can suppress a PRC/FS reset but cannot suppress the later independent `SetSwFuses` post-program callback (`mods_audit/static/decoded/all/gpuargs.js:1249`; `mods_audit/static/extracted_inner/mods`, text VAs `0xd9b020..0xd9b029`, `0xda3c91..0xda3cc4`).
- **PROVED (path-scoped):** `skip_reset_post_fusing` is also present, but its own description says it concerns post-SLT fuses that “have been blown”; the detailed xref audit places it in the physical FSP fuseblow state machine, not the direct-shadow writer (`mods_audit/static/decoded/all/gpuargs.js:1247`; `L2_REENABLE_STATIC_FINDINGS.md:1192-1198`). It is not a `SetSwFuses` no-reset switch.
- **UNKNOWN:** No inspected current host path supplies an automatic restore of old raw values after a direct-shadow failure. ### 7. Older architecture findings that must not be generalized

- **PROVED historical / UNKNOWN for GB202:** The 390.67/Type-7 and GV100 secure-PMU material proves only that older secure microcode mediated register RMW/PLM changes. The GV100 path at `0x1454bd0/0x1455240` lowering `f4/f8` neither supplies a GB202 binary/caller nor proves identical lifetime or restore semantics (`GB202_PARALLEL_WORK.md:41-46`; `L2_REENABLE_STATIC_FINDINGS.md:831-835`; `parallel/evidence_audit.md:225-236`).
- **PROVED non-applicability:** Old `SW fusing can only be disabled` callbacks belong to GM10x/GM20x/GP10x/GV100 vtables, not the Blackwell `NewFuse` vtable. They cannot establish one-way raw-shadow transitions on GB202 (`L2_REENABLE_STATIC_FINDINGS.md:1001-1009`). The current writer's plan loop is the evidence to use (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515ea0..0x15160df`).
- **UNKNOWN for TU/GA unless an explicit binding is shown:** The relevant local evidence does not bind a Turing or Ampere fuse writer, PMU flow, reset rule, or latch rule into the GB202 `NewFuse` chain. Architecture names/RTTI strings inside the multi-generation MODS executable are not call-graph evidence. The inspected GB202-aware chain is instead fixed by `0x14646f1 -> 0x14620d0` and the GB20x writer at `0x1515ea0` (`mods_audit/static/extracted_inner/mods`, text VAs `0x14643f0..0x1464720`, `0x1515ea0..0x15160df`). Accordingly, any TU/GA claim about one-way writes, PMU lowering, latch persistence, rollback, or reset type remains **UNKNOWN** for GB202 unless an explicit current vtable/HAL binding is demonstrated.

## Plain-language summary

The evidence strength is asymmetric: task 2 being intended to prepare `d0/dc` is a strong static inference, although its actual GB202 firmware effect is unproved; for separate `f8`, even intended task-2 coverage is unknown. Actual lifetime/restore for all three remains unknown.

The process-local `SecurityUnlockLevel > 3` check only admits this MODS host writer; it is not proof that the GPU will accept the write (`mods_audit/static/extracted_inner/mods`, text VAs `0x1515eb4..0x1515ed8`, `0xd5d5d0..0xd5d666`). On the normal FSP-enabled path, host-visible preparation is optional PRC handling, then task 2, then any pending host apply; `doFsp=false`/`SkipFspFs` paths must be excluded, and whether the normal send really opens `d0/dc/f8` through a later `SetSwFuses` remains unknown. `SetSwFuses` attempts the latch-set request, writes and immediately reads back every raw plan item, and resets/reinitializes only if the aggregate result is zero; ordinary mismatches fail with `0x79`, but the privilege sentinel `0xbadf510c` is only logged. An error performs host cleanup with no rollback, latch clear, or reset. A separate current GB20x resense path attempts coupling and issues the decoded latch-clear operation; only preparation-success/non-pre-silicon reaches a reset request, and type 6 depends on the coupling bits observed then, not demonstrably on this attempt. Thus “no current latch-clear path exists” is too broad, but resense is not direct-writer rollback and is not fail-closed. Older PMU, TU/GA, GH/Hopper, or certificate findings remain historical or analogical unless an explicit GB202 binding is shown.
