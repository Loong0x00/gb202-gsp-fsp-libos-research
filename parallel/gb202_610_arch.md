# GB202 / 610.43.03：KernelFsp、KernelSec2 与 NVDM 路由

## 范围与结论等级

- 仅静态阅读 `/usr/src/nvidia-610.43.03/src` 中的当前 610.43.03 开源源码。
- 未执行固件、驱动附带二进制或任何未知二进制；未访问实时 GPU、BAR0/MMIO、PCI config 或 debugfs，也未进行复位、解绑、模块或设备操作。
- 下文使用 **事实**、**强推断**、**未知** 三种等级。生成的 NVOC HAL 表也属于本版本源码事实，而不是按架构名称作出的猜测。

## 摘要

1. **事实：GB202 同时创建 `KernelFsp` 与 `KernelSec2`，但两者在本芯片上的职责并不对等。** GB202 present-list 明列两个对象；`KernelFsp` 是可工作的 MCTP/NVDM 端点，`KernelSec2` 虽存在且有一个与机密计算有关的 `StateLoad`，但其 NVDM 收发、解析和 secure-boot 消息 HAL 在 GB202 上均落到“不支持/空”桩。
2. **强推断：就本开源树能够证明的 host-RM 路径而言，GB202 的 HULK/PRC 命令只能走 `KernelFsp`，不能走 `KernelSec2`。** 这是由 GB202 的实际 HAL 绑定推出；源码没有公开任何 GB202 HULK 发送调用点，因此不能进一步声称某个实际 HULK 请求一定已由驱动发出。
3. **事实：** `NVDM_TYPE_HULK = 0x11`、`NVDM_TYPE_PRC = 0x13`，通用 FSP/SEC2 响应类型共用 `0x15`。GB202 绑定的 FSP SEID 映射把 HULK 显式放到 SEID 0；PRC 未单列，因而也落入默认 SEID 0。
4. **事实：对象构造顺序与 engine state 顺序相反，不能混为一谈。** `KernelFsp` 是 early child，先于普通 child `KernelSec2` 构造；而 GB202 的 `StateInit/StateLoad` 使用 GM200 全局顺序，其中 `KernelSec2` 在 `KernelFsp` 之前。
5. **事实：正常、未通过 override 禁用 GSP-FMC 的配置选择 FSP。** GB202 的 GSP bootstrap 复用 GH100 流程：先准备 FSP COT，随后通过 FSP 发送 `NVDM_TYPE_COT`，等待 target-mask 释放，再建立可选 SPDM 会话、发送初始化 RPC、等待 lockdown 释放和 RM init 完成。SEC2 仅是某些没有可用 FSP 分支且允许 SEC2 启动 GSP-FMC 的芯片的后备分支；GB202 不满足 SEC2 条件。若显式禁用 FSP GSP-FMC，代码会走 direct-bootstrap/报错规则，而不是自动改走 GB202 SEC2。
6. **未知：** 610 开源 host 源码没有 HULK payload 定义、HULK 调用点或 HULK 内部 task/subobject 路由表，也没有独立 floorsweep `task2/subobject1` consumer 或任一路径的专用 restore 操作。现有材料没有证明 HULK `0x11` 映射到 floorsweep task 2；因此不能仅凭此树证明任一路径的具体 PLM 降权或恢复行为。

## 1. GB202 对象存在性与角色

### 1.1 两个对象都在 GB202 present-list 中

**事实。** GB202 的 child-present 表中，`KernelFsp` 位于第 87 行，`KernelSec2` 位于第 90 行：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/arch/blackwell/kern_gpu_gb202.c:59-93`
- 生成的 GPU HAL 将 GB202 绑定到该 present-list：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_gpu_nvoc.c:1655-1657`

`KernelFsp` 的 `PDB_PROP_KFSP_IS_MISSING` 对 GB202 初始化为 `NV_FALSE`：

- `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kern_fsp_nvoc.c:232-241`

`KernelSec2` 的 `PDB_PROP_KSEC2_IS_MISSING` 也初始化为 `NV_FALSE`：

- `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.c:477-478`

因此，“对象存在”本身不能用来判断 NVDM 由谁接收。

### 1.2 GB202 的 `KernelFsp` HAL 组合

**事实。** 生成的 HAL 表给 GB202 组合了三代实现：

| 功能族 | GB202 实际绑定 | 证据 |
|---|---|---|
| FSP HAL 构造及 packet send/read/can-send/response-ready/最大包长 | GB100 | `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kern_fsp_nvoc.c:333-439` |
| secure-boot 完成等待 | GB202 专用 | `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kern_fsp_nvoc.c:489-506` |
| COT 准备/发送、SEID 映射、MCTP/NVDM 解析、command response、错误映射、target-mask 等待 | GH100 | `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kern_fsp_nvoc.c:453-481`, `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kern_fsp_nvoc.c:509-567`, `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kern_fsp_nvoc.c:585-618` |

这解释了为何 GB202 专用文件很短：它只覆盖了 secure-boot wait；消息协议并非缺失，而是由生成表显式复用 GH100/GB100 实现。

GB100 构造函数初始化 FSP mailbox aperture：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/blackwell/kern_fsp_gb100.c:76-85`

packet transport 有两个静态分支：若 `PDB_PROP_KFSP_USE_MNOC_CPU` 为真则使用 MNOC mailbox，否则回落到 GH100 packet transport；read、ready 和最大包长采用相同选择：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/blackwell/kern_fsp_gb100.c:310-417`

源码只允许 registry/property 选择该 transport；不能在不知道运行时 property 的情况下把某一个物理 transport 宣称为唯一运行态事实。

### 1.3 GB202 的 `KernelSec2` 存在，但不是 NVDM 端点

**事实。** GB202 上：

- `PDB_PROP_KSEC2_BOOT_GSPFMC = NV_FALSE`；只有 GB10B、GB20B、GB20C 为真：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.c:465-475`。
- `PDB_PROP_KSEC2_RM_BOOT_GSP = NV_TRUE`；只有 GB20B/GB20C 为假：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.c:480-489`。
- `ksec2StateLoad` 在 GB202 上复用 `ksec2StateLoad_GH100`：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.c:596-607`。该实现仅在 CC feature enabled 时为 SEC2 派生 secrets，然后返回 `NV_OK`：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/sec2/arch/hopper/kernel_sec2_gh100.c:30-45`。

但 GB202 不属于生成表中启用 SEC2 packet/NVDM 的 GB10B/GB20B/GB20C 集合。因此其以下方法全部取 default stub：

- send/can-send/max-send/read/response-ready：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.c:778-846`
- secure-boot wait、max-recv、NVDM-to-SEID、packet parsing、NVDM processing、command response、error mapping：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.c:859-955`

桩函数的实际返回值进一步确认该结论：`CanSend = NV_FALSE`、最大发送长度为 0、send/read/parse/process 返回 `NV_ERR_NOT_SUPPORTED`、`NvdmToSeid = 0`：

- `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.h:860-921`

**结论：** GB202 的 `KernelSec2` 不能因为对象存在就被视为 HULK/PRC 接收端；在 610.43.03 开源 HAL 中，它没有可工作的 NVDM transport。

## 2. NVDM、HULK 与 PRC 路由

### 2.1 类型与 framing

**事实。** 共享 NVDM namespace 定义：

- HULK `0x11`
- PRC `0x13`
- COT `0x14`
- FSP response `0x15`
- SEC2 response 是 FSP response 的别名，即同为 `0x15`

证据：`/usr/src/nvidia-610.43.03/src/nvidia/arch/nvalloc/common/inc/nvdm_format.h:37-59`。

NVDM header 是 MCTP 第二个 DWORD：message type 为 Vendor Defined PCI、vendor ID 为 `0x10de`，NVDM type 位于高字节：

- `/usr/src/nvidia-610.43.03/src/nvidia/arch/nvalloc/common/inc/mctp_format.h:39-58`
- `/usr/src/nvidia-610.43.03/src/nvidia/arch/nvalloc/common/inc/mctp_format.h:96-118`

通用 FSP sender 先调用 `kfspNvdmToSeid_HAL`，再生成 MCTP transport header 和 NVDM header；多包时只有首包带 NVDM header，后续包沿用同一 SEID：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/kern_fsp.c:508-570`

### 2.2 HULK

**事实。** GB202 绑定的 `kfspNvdmToSeid_GH100` 对 `NVDM_TYPE_HULK` 显式返回 SEID 0；INFOROM 才返回 1，其余类型也默认返回 0：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:267-302`
- GB202 对该函数的绑定：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kern_fsp_nvoc.c:509-519`

**强推断。** 若当前 610 的某个未公开/树外调用者在 GB202 上调用公开于对象内的通用 FSP send API 并指定 type `0x11`，host transport 会将其作为 FSP NVDM、SEID 0 发出。由于 GB202 SEC2 的 send/NVDM HAL 是桩，这棵源码树不存在同等可行的 SEC2 HULK route。

**未知/负证据。** 对整个 `/usr/src/nvidia-610.43.03/src/nvidia` 的 C/H 源码检索中，GPU 侧 HULK 只有：

- 类型常量：`/usr/src/nvidia-610.43.03/src/nvidia/arch/nvalloc/common/inc/nvdm_format.h:44`
- FSP SEID case：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:295`
- 另一个只适用于 GB20B/GB20C 的 SEC2 SEID case：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/sec2/arch/blackwell/kernel_sec2_gb20b.c:177-199`，而 GB202 未绑定它。

没有 HULK payload struct、HULK sender、HULK task/subobject 表、签名校验实现或 HULK 专用 response/restore symbol。因此本源码不能证明：

- HULK 在 FSP 内部落到哪个 task（包括不能证明 task 2）；
- payload 中是否存在或如何解释 subobject 1；
- 某个 HULK 请求是否降低、恢复任何 PLM；
- HULK 授权材料的签名、设备绑定或 replay 规则。

这些都属于 firmware 内部或未公开调用层，而不是当前 host-RM 开源代码所披露的事实。

### 2.3 PRC

**事实。** PRC 没有独立的 SEID case，因而在 GB202 使用的 FSP 映射中走 default SEID 0：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:290-299`

本树唯一显式的 GPU PRC caller 是 GH100 的 protected-PCIe firmware capability 查询。它构造 PRC read object 并直接调用 `kfspSendAndReadMessage(..., NVDM_TYPE_PRC, ...)`：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/arch/hopper/kern_gpu_gh100.c:542-603`

但该 caller **不适用于 GB202**。生成表只在 GH100 绑定 `gpuIsProtectedPcieSupportedInFirmware_GH100`，GB202 走默认 `NV_FALSE` stub：

- `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_gpu_nvoc.c:2417-2432`
- stub：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_gpu_nvoc.h:5443-5445`

FSP error mapping 确实认识 PRC invalid-knob error，并映射为 `NV_ERR_INVALID_ARGUMENT`：

- 定义：`/usr/src/nvidia-610.43.03/src/nvidia/inc/kernel/gpu/fsp/kern_fsp_retval.h:24-29`
- 映射：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:1583-1608`

**强推断。** 通用 GB202 FSP transport 在协议层能把 PRC 作为 SEID 0 发送，但当前开源树没有一个实际绑定到 GB202 的显式 PRC callsite。不能把 GH100 protected-PCIe query 当作 GB202 已执行 PRC 的证据。

### 2.4 response 与“恢复操作”

**事实。** 同步 FSP 调用严格按 send -> poll -> read 的顺序执行：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/kern_fsp.c:690-747`

receive parser 只接受 `NVDM_TYPE_FSP_RESPONSE (0x15)` 或 SMBPBI，然后交给 command-response parser：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:415-453`

通用 response body 只有 `taskId`、`commandNvdmType`、`errorCode` 三个 `NvU32`；parser 记录这三个字段并将 error code 映射到 `NV_STATUS`：

- struct：`/usr/src/nvidia-610.43.03/src/nvidia/arch/nvalloc/common/inc/fsp/nvdm_payload_cmd_response.h:35-42`
- parser：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:455-500`

因此：

- **事实：** 通用 command response/ack 机制存在，并可回报实际 task ID 和原 command NVDM type。
- **未知：** host 代码没有按期望值校验 `taskId` 或 `commandNvdmType`；它只解析并记录/映射错误。
- **未知：** 没有 HULK 专用 restore/undo 消息、状态 token 或 response schema。通用 `0x15` response 的存在不能证明任何 PLM 自动恢复。

## 3. 三种不同的初始化顺序

### 3.1 对象构造：`KernelFsp` 先，`KernelSec2` 后

**事实。** `gpu_child_list.h` 将：

- `KernelSec2` 标为非 early child：`/usr/src/nvidia-610.43.03/src/nvidia/inc/kernel/gpu/gpu_child_list.h:123-130`
- `KernelFsp` 标为 early child：`/usr/src/nvidia-610.43.03/src/nvidia/inc/kernel/gpu/gpu_child_list.h:297-304`

GPU construction 先执行 early pass，再构造/更新 engine table，最后执行 ordinary pass：

- early pass：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gpu.c:479-484`
- ordinary pass：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gpu.c:500-511`
- 两次 pass 都按 `gpu_child_list.h` 展开并调用 `gpuCreateObject`：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gpu.c:1652-1689`

所以在对象构造层，顺序是：

`KernelFsp construct` -> engine table construction/update -> `KernelSec2 construct`。

`KernelFsp` construct 的局部顺序是 registry/property 初始化、missing 检查、清 async 状态、创建 timer event、构造 HAL/mailbox aperture：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/kern_fsp.c:78-105`

`KernelSec2` construct 的局部顺序是先配置 Falcon，再初始化 registry/property 并做 missing 检查：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/sec2/kernel_sec2.c:66-86`
- GB202 对 Falcon config 复用 GA102：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.c:557-570`

### 3.2 Engine `StateInit/StateLoad`：`KernelSec2` 先，`KernelFsp` 后

**事实。** GB202 使用 `gpuGetChildrenOrder_GM200`：

- `/usr/src/nvidia-610.43.03/src/nvidia/generated/g_gpu_nvoc.c:1592-1600`

原始全局顺序表中的相关相对次序是 `ConfidentialCompute` -> `Spdm` -> ... -> `KernelSec2` -> `KernelGsp` -> `KernelBus` -> ... -> `Gsp` -> `OBJFSP` -> `KernelFsp`：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/arch/maxwell/kern_gpu_gm107.c:456-499`

迭代器会过滤 GB202 present-list 中不存在的项，因此 `Gsp`、`OBJFSP` 等原始表项不应被误认为 GB202 实例；对本报告结论重要且实际 present 的相对次序是 `KernelSec2` -> `KernelGsp` -> ... -> `KernelFsp`：

- present 过滤逻辑：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gpu.c:6065-6088`
- GB202 present-list：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/arch/blackwell/kern_gpu_gb202.c:59-93`

`StateInit` 与 `StateLoad` 都按该表正向遍历：

- `StateInit`：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gpu.c:2328-2358`
- `StateLoad`：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gpu.c:2761-2830`
- unload/destroy 才反向：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gpu.c:6030-6088`

所以在 state-transition 层，`KernelSec2` 的 `StateInit/StateLoad` 早于 `KernelFsp`。这并不表示 SEC2 先接收 NVDM；它在 GB202 的 `StateLoad` 只承担前述可选 CC secret derivation。`KernelFsp` 自身没有专用 `StateLoad`，而是继承返回 `NV_OK` 的基类 no-op：

- 绑定：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kern_fsp_nvoc.c:100-105`
- 实现：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/eng_state.c:300-312`

### 3.3 Secure boot 与 GSP-RM bootstrap：FSP 是首选且 GB202 实际选择的分支

**事实。** GB202 的 FSP secure-boot wait 是专用实现。注释明确说明 Bootfsm 在 chip reset 后触发 FSP 执行，FSP 完成后写 boot-complete success；该函数只是等待成功状态：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/blackwell/kern_fsp_gb202.c:48-85`

超时错误路径记录状态、标记设备需要 reset 并生成诊断信息；本研究没有触发该路径：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/blackwell/kern_fsp_gb202.c:87-108`

GB202 的 `KernelGsp` 将 prepare/bootstrap/wait-for-GFW 绑定到 GH100 实现：

- prepare/bootstrap：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_gsp_nvoc.c:710-749`
- wait-for-GFW：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_gsp_nvoc.c:1601-1624`

正常 GSP-RM 启动的可证顺序如下：

1. 在准备完 boot/GSP-RM image 和 logging 后，`kgspWaitForGfwBootOk` 调到 `kfspWaitForSecureBoot`：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/kernel_gsp.c:5002-5047`；GH100 wait wrapper 在有 `KernelFsp` 时直接调用 FSP wait：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/arch/hopper/kernel_gsp_gh100.c:248-263`。
2. `_kgspBootGspRm` 填 WPR metadata，然后调用 `kgspPrepareForBootstrap`，之后才调用 `kgspBootstrap`：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/kernel_gsp.c:4795-4841`。
3. `kgspPrepareForBootstrap_GH100` 先准备 GSP-FMC arguments；若 FSP 存在且 GSP-FMC 未禁用，则设置 GSPRM mode 并调用 FSP prepare。只有该分支不成立且 SEC2 的 `BOOT_GSPFMC` 为真时才选 SEC2：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/arch/hopper/kernel_gsp_gh100.c:779-830`。
4. FSP prepare 首先再次确认 secure boot 完成并执行 boot-command precheck，随后构造 COT/FRTS/GSP-FMC 数据：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:1257-1289`, `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:1330-1476`。
5. `kgspBootstrap_GH100` 在 FSP 分支发送 boot command；SEC2 仍只是条件后备：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/arch/hopper/kernel_gsp_gh100.c:852-899`。
6. FSP boot command 是同步的 `NVDM_TYPE_COT` send-and-read：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/fsp/arch/hopper/kern_fsp_gh100.c:1499-1545`。
7. 发送成功后等待 GSP target-mask release；随后建立可选 SPDM session、发送 init RPC、等待 lockdown release、确认 RISC-V active，最后等待 RM init done：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/arch/hopper/kernel_gsp_gh100.c:901-934`, `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/arch/hopper/kernel_gsp_gh100.c:936-1029`。

GB202 的 SEC2 properties 已经使 SEC2 bootstrap 条件为假（`BOOT_GSPFMC = NV_FALSE`），而 FSP 对象为 present。因此在没有显式禁用 FSP GSP-FMC 的正常配置中，该路径明确选择 FSP。若 FSP 分支因 `PDB_PROP_KFSP_DISABLE_GSPFMC` 为真而被跳过，SEC2 条件仍为假，代码进入 direct `_kgspBootstrapGspFmc_GH100` 分支，而不是转到 SEC2：`/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gsp/arch/hopper/kernel_gsp_gh100.c:875-899`。

另一个 proxy helper 也有相同优先级：只要 `KernelFsp` 非空就调用 FSP；SEC2 只有在 FSP 为空、SEC2 存在且 `RM_BOOT_GSP` 为假时才会使用。GB202 的 `RM_BOOT_GSP` 恰为真：

- `/usr/src/nvidia-610.43.03/src/nvidia/src/kernel/gpu/gpu.c:7859-7888`
- property 证据：`/usr/src/nvidia-610.43.03/src/nvidia/generated/g_kernel_sec2_nvoc.c:480-489`
