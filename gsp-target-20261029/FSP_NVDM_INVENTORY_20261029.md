# GSP-RM → FSP NVDM 通信面与异常类型审计（2026-10-29）

## 范围与方法

- 对 87/87 个 GB202 可用的 GSP-RM inner ELF 做静态分析；没有向 GPU/FSP 发送消息。
- 用共同的函数序言/寄存器保存序列定位每个版本的 GSP→FSP NVDM sender wrapper。
- 在首个可执行 PT_LOAD 中解析 RV64 `AUIPC+JALR`，枚举到该 wrapper 的直接 call/tail-call。
- 对调用点前 64 字节内的 `a4`（NVDM type）做有限立即数数据流追踪，并用 Ghidra 对关键函数和调用关系复核。
- 另检查小函数 `return <type>` 及其 Ghidra xref，避免遗漏通过 HAL/vtable 间接提供的类型。

机器可读结果：

- `fsp_sender_summary.json`：87 个 sender 地址及直接调用数。
- `fsp_nvdm_calls.json/.tsv`：1,456 个直接调用点。
- `nvdm_type_getters.json`：类型提供函数及原始数据引用。

## 总体调用面

共解析到 **1,456** 个直接调用点，其中 **1,078** 个可以静态恢复立即数 NVDM type，**378** 个为动态类型。

| Type | 直接调用数 | 公开含义 |
|---|---:|---|
| `0x13` | 319 | PRC |
| `0x11` | 174 | HULK |
| `0x18` | 144 | SMBPBI |
| `0x1d` | 87 | UEFI_XTL_DEBUG_INTR |
| `0x14` | 87 | COT |
| `0x16` | 87 | CAPS_QUERY |
| `0x20` | 87 | CLOCK_BOOST |
| `0x1c` | 87 | UEFI_RM |
| `0x24` | 6 | **公开头文件未命名** |

另外，动态类型路径中存在 `0x21 FSP_GSP_COMM`、`0x23 FSP_GSP_RM_METHOD_OF_COMMS`、`0x25 RM_RPC` 和 `0x26 GMCAPI` 的 HAL/vtable 类型提供函数或映射，因此“直接立即数扫描为零”不等于这些类型没有被使用。

## 意外发现：未公开 `0x24`

610.43.02、610.43.03、610.57.04、615.71.09、615.71.10、615.78.08 各有一个直接调用点使用 **`a4=0x24`**。610 和 615 的公开 `nvdm_format.h` 没有给出该类型名称；615 公开了 `0x23` 和 `0x26`，但仍未命名 `0x24`。

610.57.04 实证：

- wrapper：`0x01af03dc`
- 调用点：`0x01af03fe`
- 反汇编明确为 `li a4,36`、`li a3,4`，随后调用公共 sender `0x0150c070`。
- 615.78.08 对应 wrapper 为 `0x01b34f1c`。

该 wrapper 具有以下特征：

- 输入为 **4 字节命令**；目前见到的实际值为 `1` 和 `2`。
- 返回缓冲区长度参数为 **17 字节**；错误时打印 4 字节输入和 17 字节输出。
- 610 的直接调用者 `0x0161a9b0` 是较大的 GPU 生命周期/状态路径，三处调用均只把返回值和错误字段用于状态处理。
- 没有看到地址、IMEM/DMEM offset、固件对象 ID、明文输出长度或大块内存回读参数。

**结论边界：** `0x24` 是真实、此前未公开的 NVDM 通信类型，但当前数据形态更像生命周期/状态命令，不像固件明文或任意内存导出通道。没有证据把 17 字节响应解释成地址；调用者也没有按地址消费它。

相关证据：`610_type24.log`、`610_type24_caller.log`、`615_type24_exact.log`。

## ROMREAD (`0x1a`) 与 `FSP_GSP_COMM` (`0x21`)

- 87 个版本中，公共 sender 的立即数直接调用里 **没有 `0x1a ROMREAD`、没有 `0x21`、没有 `0x23`、没有 `0x26`**。
- `0x21` 确实通过 vtable 间接路径使用：570 的 `0x0170a148`/`0x0170a198` 返回 `0x21`，并在 HAL 构造代码 `0x01ad95dc` 中装入对象方法；因此不能用立即数扫描否定 FSP_GSP_COMM。
- 相比之下，`return 0x1a` 的候选 ROMREAD getter 在 87 个版本中均没有 Ghidra xref。以 570.86.16 的 `0x016a7e44` 为例，没有直接调用或数据安装引用。
- 动态类型调用还存在 RM RPC/GMCAPI/方法协商等路径，不能把全部动态调用都归为 ROMREAD。

**结论边界：** 当前 GSP-RM 消费面没有建立一条可用的 ROMREAD→FSP_RUN 明文路径。`0x1a` getter 的“函数存在但未安装/未引用”与直接调用缺失是相互支持的双证据，但仍不能据此否定芯片 ROM、UEFI、FSP 内部或其他未公开消费者。

## 对 FSP_RUN 明文获取的实际意义

1. 新类型 `0x24` 值得记录，但目前没有地址形参或明文输出语义，**不是可复用 oracle**。
2. 已确认的动态类型通道说明仅扫立即数会漏报；后续分析必须保留 vtable/间接调用，而不能把公开 host API 当作完整边界。
3. 目前没有从 NVDM 通信面得到新的 FSP_RUN plaintext 地址。不能把 `0x24` 的 17 字节响应、CAPS 响应、DMEM log 或普通 RM RPC 响应解释为 FSP_RUN 代码。
4. 下一步若继续，应优先追踪**不透明响应缓冲区的生产者、动态 RPC 方法映射和 FSP/ROM 内部消费者**，而不是把这些通信类型直接喂入 FSP_RUN 密文做实验。
