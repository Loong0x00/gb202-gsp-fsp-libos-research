## Vulnerability class

- Persistent denial of service against device-management firmware services
- Improper recovery or persistent fail-closed state after malformed management traffic
- Possible incomplete validation or error rollback in the FSP NVDM runtime dispatcher

## Summary

After a sequence of malformed NVDM and transport probes, a GB202 FSP runtime dispatcher stopped replying to all tested runtime NVDM services.

Earlier project records contain successful PRC and firmware-update status responses on the selected XOC VBIOS slot. However, the raw same-day log immediately before the first malformed probe establishes successful GSP boot and clean queues, not a fresh PRC/FWUP response. This distinction is important when assessing causality.

The immediate MNOC transport error bits could be cleared by a complete power cycle, but the higher-level FSP runtime services remained unresponsive. The FSP boot path continued to operate and could still boot GSP-RM, so normal GPU compute and display operation remained available. The unavailable services included PRC, firmware-update status, capability query, InfoROM, and clock-boost requests.

The malformed requests were **not** generated by the repository's `rom_read_nvdm()` helper. In particular, they did not include the documented `[offset, size, 0]` request payload and did not use `SEID=1`.

## Security impact

A privileged local actor with direct MMIO access to a passed-through GB202 GPU may be able to place the FSP runtime management plane into a state that survives normal software resets and a complete removal of system power.

Observed unavailable functionality included:

- PRC knob read/write services;
- FSP firmware-update status/services;
- FSP capability query;
- InfoROM object services;
- clock-boost management services.

The GPU itself remained usable after GSP boot: `nvidia-smi` and CUDA operation continued to work. The practical impact is persistent loss of the device's management and recovery plane, potentially requiring a vendor service procedure or physical flash recovery.

No cross-tenant impact or unprivileged attack path is claimed in this report. The historical trigger required privileged direct access to GPU MMIO in a VFIO guest.

## Preconditions

- Full physical GPU passthrough to a VM, or equivalent privileged BAR0 access.
- Ability to write the FSP MNOC mailbox registers.
- A previously functioning FSP runtime service on the selected VBIOS slot, according to earlier project controls.

## Baseline evidence and limitation

Earlier project records on the selected XOC slot include valid responses to:

- a PRC request over MNOC port 1;
- firmware-update command 6/status query over MNOC port 1.

In the raw 10/02 session immediately before the first malformed probe, the directly preserved controls are:

- successful clean-module/GSP initialization;
- successful `nvidia-smi` device enumeration;
- empty FSP CMDQ and MSGQ;
- clean MNOC port 0 and port 1 receive state (`0x85000000`) after the first EMEM probe.

A fresh PRC or FWUP response immediately before the malformed sequence is not present in that raw log. The report therefore treats the prior healthy runtime state as supporting context, not a perfect same-boot control.

## Historical trigger sequence

### Step 1 — malformed EMEM probe

The first recorded `0x1A` operation was an approximately 64-byte EMEM probe with this semantic content:

```text
0x1A10DE7E
0x00000017
0x00700001
0xFFFFFFFF repeated 13 times
```

It reused unrelated buffer content and omitted an MCTP header. No MSGQ response was observed. Later queue testing showed that writing QH=0 also clears QT, so queue pointers returning to zero do not prove that FSP consumed this request.

### Step 2 — ineffective wrong-register MNOC attempt

A subsequent three-word `0x1A` attempt wrote the wrong mailbox direction/registers. It produced no error and is not counted as a valid transmission.

### Step 3 — actual MNOC framing used

The request consisted of three 32-bit words:

```text
word 0: 0xC0000001    MCTP single-packet header, default SEID 0
word 1: 0x1A10DE7E    NVIDIA vendor-defined message, NVDM type 0x1A
word 2: 0x00000000    only payload word
```

This is malformed relative to the current `gpu-admin-tools` helper:

```python
send_message = [offset, size, 0]
return self.send_cmd(0x1A, send_message, timeout=10, seid=1, ...)
```

The historical request therefore omitted `offset` and `size` and used the default SEID rather than `SEID=1`.

### Step 4 — port 1 request

Before transmission:

```text
MNOC port 1 INFO_RECV = 0x85000000
receive_ready = 1
credit_available = 1
error = 0
```

The three words above were written through port 1. Immediately afterward:

```text
MNOC port 1 INFO_RECV = 0x8600000c
error = 1
```

No FSP response packet was observed.

### Step 5 — port 0 request

Without first restoring and independently validating the full FSP runtime state, the same three words were then sent through port 0.

Before transmission:

```text
MNOC port 0 INFO_RECV = 0x85000000
```

Immediately afterward:

```text
MNOC port 0 INFO_RECV = 0x8600000c
error = 1
```

### Subsequent attempts

The investigation then sent another 12-byte EMEM request containing `0xC0000001, 0x1A10DE7E, 0x00000000`, followed by PRC, FWUP, channel-state, reset, and message-format diagnostics. Several later PRC probes were themselves malformed. These operations are confounders; this report does not claim that the first EMEM probe, the port 1 request, or the port 0 request alone is sufficient.

A later clean-port test also showed that malformed PRC framing can produce the same `0x8600000c` MNOC error. The immediate ERR latch therefore demonstrates transport rejection, but is not unique evidence that a valid ROMREAD handler executed.

## Post-incident observations

After subsequent restarts, tested runtime services either returned a transport error or timed out. After a complete power removal, the transport mailbox returned to a clean ready state:

```text
MNOC port 1 INFO_RECV = 0x85000000
error = 0
```

A known-good PRC read request was accepted by the mailbox but produced no response:

```text
request: 0xC0000001 0x1310DE7E 0x001D020C
result:  timeout
INFO_SEND = 0x00000000
INFO_RECV = 0x85000000
```

The same no-response behavior was observed for:

```text
PRC          NVDM 0x13
FWUP         NVDM 0x12
CAPS_QUERY   NVDM 0x16
INFOROM      NVDM 0x17
CLOCK_BOOST  NVDM 0x20
```

A manually tested EMEM runtime request also produced no response.

FSP boot operations remained functional enough to boot GSP-RM. `nvidia-smi` and CUDA continued to operate, distinguishing the failure from total FSP or GPU failure.

## Persistence and recovery attempts

The no-response runtime state was observed after the following recovery attempts:

- NVIDIA driver unload/reload;
- VM restart;
- PCIe FLR;
- PCIe secondary-bus reset;
- D3hot/runtime power-management cycles;
- a user-reported complete host power cycle and removal of system power (the exact off-time was not recorded in the raw message);
- subsequent bare-metal driver initialization.

A VBIOS-slot switch did not provide a clean comparison because the other slot had pre-existing COT/WPR2 damage. This report therefore does **not** claim that one malformed request modified both VBIOS flash devices.

## Expected behavior

One of the following would be expected:

1. reject a malformed request with an error response while keeping the dispatcher operational;
2. reset only the affected transport endpoint;
3. recover the runtime dispatcher after a fundamental reset or full power cycle;
4. reject host-origin traffic for a GSP-only endpoint without persisting a device-management outage.

A malformed request should not leave unrelated FSP runtime services unavailable across full power cycles.

## Actual behavior

- Both tested MNOC ports latched an immediate error on the truncated `0x1A` packet.
- The same ERR signature was later reproducible with malformed PRC framing, so the latch is a transport-rejection indicator rather than proof of ROMREAD execution.
- After the immediate error condition was cleared by reset/power cycling, the runtime dispatcher accepted mailbox writes but generated no responses to correctly framed PRC and other runtime service probes.
- All tested runtime service families remained unavailable.
- The separate boot dispatcher remained functional.

## Evidence limitations

- The minimum sufficient packet sequence is not known.
- The first recorded `0x1A` probe was a malformed EMEM message, before the effective MNOC transmissions.
- Port 1 and port 0 were tested sequentially without a complete restore between them.
- Another EMEM attempt, malformed PRC probes, resets, and additional diagnostics followed.
- The raw same-day log lacks a fresh successful PRC/FWUP response immediately before the first malformed probe; prior healthy runtime controls exist in earlier project records.
- The `0x8600000c` mailbox ERR value is not unique to NVDM `0x1A` and can also be caused by malformed PRC traffic.
- No complete pre/post 4 MiB SPI flash image exists, so persistent flash modification has not been demonstrated.
- The exact persistent object or firmware state has not been identified.
- The official `rom_read_nvdm(offset, size)` helper was not executed and is not alleged to be affected.
