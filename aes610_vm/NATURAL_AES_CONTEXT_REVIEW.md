## 结论摘要

- `C` 是传给 `1bf4208` 的第二个参数，也是自然调用者 `1a8d588` 在栈上构造的上下文对象；`1bf4208` 把它挂到内部临时对象的 `+8`。已知 `C+0x30` 是 key bits、`C+0x34` 是 slot index。
- `C+0x60` 是指向 16 字节 sidecar/control block 的指针；自然调用者把它指向自己的栈上块。
- `C+0x68` 是必须非零、并通过低 40-bit 检查的后端地址/不透明 token。自然调用者从选择器索引表取值；当前反汇编不能把它进一步命名成 CPU VA、GPU VA 或物理地址。
- `C+0x78` 是阶段状态字，不是返回错误码。自然初值为 `1`，AES 路径推进到后续阶段值。
- `request+0/+8` 是两个经过自然地址窗口转换的地址槽；`request+16/+20` 是同一个长度的两个 32-bit 副本，不是地址。
- 真正的函数返回状态在 `a0`；自然完成量 readback 是 `C+0x70`，且自然调用者会将其与请求长度比较。`C+0x74` 是另一阶段的计数。
- 目前只能给出调用 ABI 形状，不能据静态证据声称有一个已知答案 AES 调用可直接成功。缺的是实际运行时自然 `C` 实例及其有效后端 token/地址映射和可读回的目标地址。

## 1. `C+0x60 / +0x68 / +0x78`

| 字段 | 610.57.04 反汇编能证明的语义 | 自然取值来源 |
|---|---|---|
| `C+0x60` | 指针。`1bf4362` 在 `C+0x1a` 非零时，写 `*(u32 *)(*(u64 *)(C+0x60)+12) = 0x01000000`（`1bf4392–4398`）。所以它指向可写的 sidecar，而不是 AES 输入/输出地址。 | `1a8d588` 将 `C+0x60` 设为栈上 16 字节块地址（C 基址为 `s0-256`，sidecar 为 `s0-272`；`1a8d826`）。自然路径先清 16 字节、从该调用的参数 `s1` 复制 12 字节，再将块 `+12` 置为 `0x01000000`（`1a8d7c0–7f2`；复制 helper `18bd9d8` 的参数/拷贝循环也在 ELF 中）。`1bf4362` 可再次写入同一标志。 |
| `C+0x68` | 必须非零的 64-bit 后端地址/token（`1bf4362` 的 `1bf43e4–43e8`、`1bf45da` 的 `1bf45fe–4600`）。在 `1bf45da` 中它被送入 identity helper，再经 `1bf691a` 检查高 24 位必须为零；该代码没有解引用它。因此“后端地址/token”是证据边界，不能仅凭此称为 CPU/GPU/物理地址。 | `1a8d588` 从 `0x41d40b4` 取 selector，以 `0x1e140c8 + selector*4` 查表（selector 检查 `<=9`，`1a8d616–636`）；表项 `lw` 保存到栈后装入 `C+0x68`（`1a8d652`、`1a8d83c–84c`）。实际表项及其有效性是运行时值。 |
| `C+0x78` | 32-bit 阶段状态字：零值会被拒绝；`1bf4362` 根据当前阶段执行首段，`1bf45da` 处理后续阶段。相关路径将状态置为 `2/3/4`；它不是 `0xf0` 这类函数状态码（`1bf43a2–43c2`、`1bf4546–45b2`、`1bf4680–4698`）。 | 自然调用者将 `1` 写入 `C+0x78`（`1a8d802` 周围初始化后，`1a8d82a`；C 基址 `s0-256`）。后续值由 AES 路径更新。 |

自然调用者还将 `C+0x30` 写为常量 `256`，`C+0x34` 写为其入口参数（`1a8d858–870`）；`1bf3caa` 检查 slot `<=15`，并检查支持的 key-width 路径（`1bf3cde–d00`）。

## 2. `request+0/+8/+16/+20`

`1a8d464` 构造 24 字节 request 并调用 `1bf4208(&request, C)`：

| 偏移 | 自然写入值 | 证据/说明 |
|---|---|---|
| `+0` | `map(arg1)` | `1a8d464` 将入口 `a1` 传给 `1aa386a`，把转换结果写到 request `+0`（`1a8d49e–4dc`）。 |
| `+8` | `map(arg2)`；若 `arg2==0` 则为零 | 第二个转换只在 `arg2` 非零时执行（`1a8d4ba–4ce`），结果写 request `+8`（`1a8d4d4–4e6`）。 |
| `+16` | `u32 arg3`（长度） | `1a8d4d8`。 |
| `+20` | 同一 `u32 arg3`（长度副本） | `1a8d4ea`。 |

`1aa386a` 并非原样传递指针：它在全局注册的地址窗口中查找输入地址，并按对应窗口的 base/size/paired-base 做 `address + (paired_base - base)` 转换；未命中返回 `31`（函数末段 `1aa3966–3988`）。因此 `+0/+8` 是转换后的地址别名，而非已证实的 raw CPU pointer、GPU VA 或物理地址。符号被剥除，静态证据不能给这些窗口贴上更具体的域名。

`1bf4208` 将 request 的 24 字节复制到临时对象 `+0x10` 起始处，然后把 `C` 放到临时对象 `+8`；随后执行 `1bf4362`、成功后执行 `1bf45da`（`1bf421c–4272`）。自然调用者 `1a8d588` 的一条路径调用 `1a8d464(C, arg1, 0, n)`，所以该次 `request+8` 为零；其它分段调用可传入第二地址。`1a8d464` 成功后对 `request+8` 和长度调用 `1a9e45c`，该地址处的当前指令是 `fence io,io`，这证明有完成屏障，不证明它读取、比较了密文。

## 3. 返回状态与 readback

- `1bf4208` 的 `a0` 是直接返回码：下层成功值按 `0xf0` 比较；错误路径保留相应的非成功码（`1bf4256–42a8`）。因此直接调用时应检查 `a0 == 0xf0`，不能把 `C+0x78` 当作这个返回码。
- 自然封装 `1a8d464` 将 `0xf0` 成功转换为自身返回 `0`；地址映射错误会传播，AES 操作失败路径返回 `56`（`1a8d4ee–528`、`1a8d55e–57a`）。`1a8d588` 用 `bnez` 检查这个自然封装返回值（例如 `1a8d8ce–8e2`）。
- 最清晰的自然 readback 是 `C+0x70`（十进制 `+112`）：`1bf4362` 成功后将 request 长度累加到它（`1bf451e–4542`）；自然调用者随后将 `C+0x70` 与预期长度比较（`1a8d8e6–8ea`）。`C+0x74`（`+116`）在 `1bf45da` 的后续阶段累加长度（`1bf4624–4656`）。这些是进度/长度 readback，不是 AES 输出正确性的证明；输出字节仍需通过自然第二地址另行读取并与软件 KAT 比较。

## 4. 最短调用形状与仍缺的自然对象

静态可确认的最短 ABI 形状是：

```text
request = { translated_arg1, translated_arg2_or_0, n, n }
rc = 1bf4208(&request, C)
```

自然调用者 `1a8d588 -> 1a8d464 -> 1bf4208` 提供了 `C` 的构造模板：`C+0x30=256`、`C+0x34=入口 slot`、`C+0x60=&sidecar16`、`C+0x68=selector-table 项`、`C+0x78=1`；其 `C+0` 也来自运行时 backend/context 查找（`1bf26b0` 路径）。但是 selector-table 内容、有效的 `C+0/C+0x68`、地址窗口映射值以及一对真实输入/输出地址，都是动态对象/状态，不是 ELF 中可以代入的常量。

因此当前不能写出“已知答案调用会成功”的配方。缺少的关键对象是**实际构造完成的自然 `C` 实例（尤其是有效的 `C+0` 与非零 `C+0x68` backend token）**，并且 request 地址必须落在 `1aa386a` 注册窗口内；还需要可读回的自然输出地址。仅合成 24 字节 request、猜测 `C+0x68` 或把 `C+0x78` 当状态 readback，都不足以构成静态可证的 KAT 调用。
