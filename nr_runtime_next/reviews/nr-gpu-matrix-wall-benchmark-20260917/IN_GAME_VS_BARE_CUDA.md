# Why in-game NR is faster than the bare CUDA call

## Observed values

### Bare public CUDA API

- 3840x2160: steady GPU event span about **9.27 ms**.
- 6144x3456: old run about **19.99--20.38 ms**; current long A/B runs about **21.0--21.2 ms**.
- Nsight Systems summed kernels: **7.726 ms at 4K**, **18.442 ms at 6K**.
- The 512 case makes the non-kernel interval especially visible: 4.418 ms event span versus 1.929 ms summed kernels, with about 156 launches/frame.

### In-game graphics-API path

The preserved WuWa timestamp stream brackets Feature 18 directly in the Vulkan command buffer. For output 6144x3456:

- DLAA metadata group, 1,652 samples: median **16.9338 ms**, p10 **16.8467 ms**, p90 **17.5666 ms**.
- UltraPerformance metadata group, 7,240 samples: median **17.1877 ms**.
- Quality metadata group, 2,167 samples: median **17.5451 ms**.

The near independence from render resolution confirms that output resolution controls most of the cost.

Community RTX 5090 full-4K reports are about 7.2 ms for one pass; broader published tests report roughly 7.9 ms. Those numbers are graphics-queue timestamp intervals and are consistent with the bare 4K kernel sum, not with the bare CUDA event span.

## Primary cause: different execution backend

The bare probe calls `NVSDK_NGX_CUDA_EvaluateFeature`. Its approximately 156 operations are submitted through Wine's `nvcuda` CUDA-driver route.

The in-game bridge calls `NVSDK_NGX_VULKAN_EvaluateFeature`. The DLL requests `VK_NVX_binary_import`; this API imports NVIDIA CUBIN functions and records their launches into a Vulkan command buffer (`vkCmdCuLaunchKernelNVX`) before queue submission. It is effectively a batched graphics command stream, conceptually closer to CUDA Graph replay than to 156 individual public CUDA launches.

Both exported wrappers eventually call the same internal evaluator at `0x180018620`, but with different backend objects. Therefore the model/weights can be the same while launch, dependency, resource and synchronization handling differ.

The numerical match at 4K is strong evidence:

- CUDA event span: about 9.27 ms
- summed useful kernels: about 7.73 ms
- in-game/community graphics-API pass: about 7.2--7.9 ms

At 6K, the graphics route also avoids a substantial part of the CUDA timeline's dispatch/wait interval. Exact attribution of every remaining millisecond requires a game-side per-kernel Nsight trace, but the backend difference is already directly established.

## Excluded explanations

### Surface precision is not the main cause

A guarded CUDA A/B changed every public CUDA array from FP32 to FP16:

- FLOAT1 median GPU: 21.1150 ms
- HALF median GPU: 20.9646 ms
- FLOAT2 median GPU: 21.1950 ms

The A-B-A difference is only about 0.19 ms, nowhere near the 3--4 ms game/CUDA gap.

### It is not merely higher clocks in-game

During the bare A/B, the RTX 5090 was already P0 with approximately:

- 2.73 GHz median graphics clock under load
- 17,001 MHz memory clock
- about 599 W median sampled load power
- about 87% median sampled utilization

So game warm-up or boost residency cannot explain why the game pass is faster.

### The 6K guide/create compatibility contract is not sufficient on CUDA

A second CUDA experiment emulated the game's 4096x2304 guide/input metadata and temporary 0.5 CreateFeature compatibility path while retaining a 6144x3456 color/output surface. Median GPU time remained **21.15 ms**. Thus the guide clamp alone does not produce the game result on the CUDA backend.

### Reset/history does not explain it

Both comparisons use reset only on the first frame and measure consecutive reset=false frames afterward.

## Timing-definition caveat

The values are not CPU-call duration:

- Bare `gpu_ms` is a CUDA-event interval around EvaluateFeature on its CUDA stream.
- Game `feature18_ms` is a Vulkan GPU timestamp interval around the Feature 18 commands.

They both measure GPU-queue work, but the commands being timed were generated by different backends. That distinction is the result, not a measurement mistake. Game total timing additionally includes codec/interop; the quoted 16.9--17.5 ms is Feature 18 alone.

## Conclusion

The bare CUDA harness is a correctness oracle and a conservative CUDA-path wall benchmark; it is not the representative game performance path. For expected in-game cost, use graphics-API timestamps:

- RTX 5090 4K: roughly **7--8 ms**
- this WuWa 6K path: roughly **17 ms**

The current evidence says the advantage mainly comes from Vulkan/D3D command-buffer submission of imported CUBIN work, avoiding public-CUDA/Wine launch and synchronization overhead. Do not optimize the model based solely on the 9/20 ms bare numbers.
