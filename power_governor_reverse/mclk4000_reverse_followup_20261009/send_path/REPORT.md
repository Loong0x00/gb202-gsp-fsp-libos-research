# MODS 570.215 +4000：PMU command-0 发送路径独立复核

范围：仅静态检查匹配 runtime PMU ELF 的指令及已有日志标记；未启动 MODS、未访问 GPU、未修改固件或旧目录。目标 ELF SHA-256：`2eef42f0b434990d2c9669124199a912e8e16d8480d1c9a74d46d75e1575b93b`。

## 结论

**是：这次故障对应的 PMU CPU 执行流已越过 command-0 的两个 MMIO store，进入完成等待；因此可以确认 CPU store 指令路径实际执行，不只是准备/尝试发送。** 日志 mailbox1=`0x25728` 对应 primitive `0x205d1acc–0x205d1ad4` 的等待失败标记，处理器将陷入时 `a0` 保存后上报；不是入口处标记 `0x256c8` 的 busy 分支。

这只能证明 PMU CPU 发出了 store（写请求），**不能证明总线/寄存器端点接收、命令被消费或成功执行**。现有指令也不能判定端点收到的 payload 值具体是多少，因为该值运行时从 wrapper 的输入缓冲区加载。

## 不可绕过的序列（就本次 mailbox 标记所指控制流）

1. `0x206358ca` wrapper 调用 primitive `0x205d19ce`：`a0=0`（command 0），`a1=&halfword`，`a2=&word`，`a3=95000`（`lui 0x17; addi 0x318`），`a4=0`（非 direct）。wrapper 在 `0x206358f8–0x2063591c` 准备这两个输入字段。
2. primitive `0x205d19ce` 保存寄存器，随后 `0x205d1a64–0x205d1a76` 先后调用 helper `0x205d496a` 两次。对应执行序列是：
   - `0x205d1a64–0x205d1a6c`：地址参数 `0x9a4514`（helper 内转为 `0xc09a4514`）、值参数为 `lw a1,0(*a2)` 的 payload；调用 helper 写该地址。
   - `0x205d1a70–0x205d1a76`：值改为命令字 `s2`，地址参数 `0x9a4504`（helper 内转为 `0xc09a4504`）；再次调用 helper。
   - 所以按寄存器偏移，**payload/DATA `+0x14` 先写，命令/触发 `+0x04` 后写**。命令字组成为 `(cmd << 8) | seq8 | (halfword << 16)`：`0x205d1a3a–0x205d1a58`。对 command 0，低命令字段为 0，另外包含递增的 8-bit 序号及输入 halfword 字段。
3. `a4=0` 导致 `0x205d1a7a` 选择普通等待分支（而非 `a4!=0` 的另一路）。`0x205d1ac6` 调用等待 helper；若成功则 `a0==0` 并走 `0x205d1ad6` 后续检查/完成返回。实际故障路径在 `0x205d1aca` 检查到非零，`0x205d1acc–0x205d1ad4` 将 `a0` 设为 `0x25728` 并跳到共享 `ebreak` `0x205d1a2c`。
4. 异常处理器 `0x205cba5a` 将异常时 `a0` 保存至 frame `+0x48`；`0x205ca588–0x205ca596` 取回并写 mailbox1（`lui 0x6047b; slli 1; +0x454`，即 `0xc08f6454`）。故日志标记与这个等待失败分支吻合。运行流只有在执行完 `0x205d1a6c`、`0x205d1a76` 两次 helper 后才到达 `0x205d1ac6` 等待；据此可确认两条 store 路径已走过。

## Helper、屏障及确认边界

`0x205d496a` 将输入地址低 32 位变成 `0xc0000000 + offset`（`0x205d4976–0x205d4982`）。若 `tp+9 != 0`，`0x205d498a` 直接执行 `sw a1,0(s1)`。否则先调用 `0x205cef04`，然后 `0x205d499a–0x205d49a4` 执行 CSR `0x895` 清位、`sw`、置位，最后跳 `0x205cef52`。这看起来是对受保护 store 的临界区/中断状态管理；无论哪条路径，指令中都**没有显式 RISC-V `fence`/`fence.i`，没有从目标 MMIO 地址读回，也没有 posted-write flush/readback**。helper 的前后调用及 CSR 操作不能等同于硬件端点确认。

从静态控制流能证明的是：PMU 到达发送调用、执行相应 CPU store 指令路径，并继续进入完成等待；失败发生在等待返回非零。不能由此区分写请求未到达、端点未处理、完成事件未产生/未送达或 PMU 等待协议未匹配，也不能证明设备端收到或接受 payload。

## 指令复核

本报告基于 llvm-objdump 对目标 ELF 直接反汇编，主要区间：

- primitive：`0x205d19ce–0x205d1b52`
- helper：`0x205d496a–0x205d49b2`
- helper 前后临界区钩子：`0x205cef04–0x205cef50`、`0x205cef52` 起
- wrapper：`0x206358ca–0x20635978`
- 异常保存/上报：`0x205cba5a`、`0x205ca588–0x205ca59a`

关键未知：目标 MMIO 寄存器的设备侧语义/消费者；此特定日志运行时 `*a2` payload 的值；写事务是否在设备端被接受；完成超时究竟是消费失败还是通知/等待链路问题。`+0x14=DATA`、`+0x04=CMD` 是依据写入顺序及协议用途的寄存器角色描述，固件本身未提供可读符号名。
