# MODS 570.215：MCLK `+3999 / +4000 MHz` 边界的静态结论

日期：2026-09-03  
范围：仅本地二进制、固件、VBIOS 与既有日志；没有启动 MODS、没有访问 GPU、没有执行频率/电压测试。

## 结论

`+4000 MHz` 不是 MODS 参数解析上限，也不是 host RM 的普通越界拒绝。现有证据闭合出的故障顺序是：

```text
-dramclk 18001
  -> relation 12 offset = 18001000 - 14001000 = 4000000 kHz
  -> host RM 接受控制值并进入 PMU change sequence
  -> MCLK change sequence 内一个较早的共享硬件-mailbox事务未完成
  -> 后续 MCLK command-0 请求发现 mailbox busy
  -> PMU 在 0x205d1a2c 执行 ebreak
  -> PMU halt
  -> host 等待 CHANGE_SEQ_PMU 4000 ms 后返回 NV_ERR_TIMEOUT (0x65)
```

因此，日志中的 `4000000 kHz` 是触发该路径的输入边界，但 `SEPC=0x205d1a2c` 是**后续 mailbox 重入断言**，不是最初的 VF 计算错误点。

目前没有静态证据支持一种可安全提交 38 Gbps（MCLK 19000 MHz）的绕过。修改基准、分两次提交、改用另一个 setter 或直接写 PLL 都不能证明会避开最终 MCLK change sequence；其中直接 PLL/校验绕过还会跳过 GDDR7 转换和训练语义。

## 1. 数值边界

故障 MODS 环境的 P-state/MCLK 最后一个编程键为 `14001000 kHz`：

- 18000 MHz：`18000000 - 14001000 = 3999000 kHz`，通过；
- 18001 MHz：`18001000 - 14001000 = 4000000 kHz`，在显存测试开始前失败；
- 19000 MHz：`19000000 - 14001000 = 4999000 kHz`。

18000 MHz 的硬件测量约为 17982 MHz。17751、17876、17938、18000 MHz 的已有测量都近似请求值乘以 `1000/1001`，没有证据显示 18001 MHz 先进入显存测试后才因误码失败。

## 2. host RM 为什么没有拒绝 4000000 kHz

### 2.1 相关 VBIOS/运行时公开范围允许到 +5000 MHz

本机保存的 512 KiB sysfs VBIOS：

- `/home/user/rt_5090_project/lact_contract_confirmation_20260817_0448/live-vbios-sysfs-full.rom`
- SHA-256 `f9a4bcf866c216f633ca322d14ff9de02e8238aeee93ebe7de0a20ab9c5f77cf`

其全部非零映像区 `0x00000..0x279ff` 与完整 Astral/XOC ROM `281814.rom` 的对应 expansion image 字节一致；sysfs 文件从 `0x27a00` 起只是零填充。完整 ROM 为：

- `/home/user/rt_5090_project/vbios_bulk_5090_20260723/downloads/manual_from_downloads/281814.rom`
- SHA-256 `0a1a511e72d707f513aab02a1d1ccfa8a78347d56915b0c922398724193ec97d`

该 ROM 的 Clocks v0x50 MCLK 项：

```text
relation range = 8..12
raw dword       = 0x1388fc18
signed limits   = -1000..+5000 MHz
```

当前 R610 运行时 `CLK_DOMAINS INFO` 也独立报告 MCLK offset range 为 `-1000..+5000 MHz`。所以 host 侧接受 `+4000 MHz` 与公开对象信息一致。

注意：生产驱动运行时曾把 relation 12 显示成 15001 MHz、总 factory offset 为 +1000 MHz；本次 MODS 故障日志的实际计算基准仍是 14001 MHz。两者不能混算。

### 2.2 host RM 的比较是正常的有符号、包含端点比较

正确 MODS ELF 中：

- `0x6e204c0`：VF-relation control SET 验证与应用；
- `0x6e20340`：取得最大 OC offset；
- `0x6e201c0`：取得最小 OC offset。

控制记录至少已恢复为：

```text
params +0x04  enable/控制头起点
params +0x08  signed frequency offset, kHz
relation object +0x58  relation index
relation object +0x74  保存的 8-byte control state
```

`0x6e204c0` 执行：

```c
if (offset <= max && min <= offset)
    apply_control();
else
    return NV_ERR_OUT_OF_RANGE; // 0x3f
```

失败日志没有出现其范围错误字符串：

```text
NVRM: Input freq OC offset is outside the allowed range...
```

而是继续进入 PMU/change-sequencer。因此不能把本次问题解释成“host RM 本应拒绝但整数比较溢出”。

另一个 `0x6e45b80` 验证器也明确读取 clock-domain 对象的两个有符号 16-bit MHz 边界，乘 1000 后比较；它对应另一个 clock/VF-point control 路径，不是整数宽度异常。

## 3. `fileid 0x000bfe:1225` 不是 4,000,000 边界检查

`<fileid:0x000bfe>` 对应代码区 `0x6b12610` 的 Falcon debug-info 路径。源行 1225 对应 `0x6b1284b..0x6b128a9`：当 Falcon 状态为 2/3 且调试条件未置位时，它输出通用断点：

```text
NVRM: bp @ <fileid:0x000bfe>:1225 (reason=112)
```

这段代码不读取 VF offset；它是在检测/转储已经异常的 Falcon。把该 fileid 行当作 `+4000` 的直接比较点是错误的。

日志后部给出的真正 host 结果是：

```text
_threadNodeCheckTimeout: Timeout was set to: 4000 msecs!
CHANGE_SEQ_PMU timed out waiting - changeSeqId=...
Error in change sequencer: status = 0x00000065
```

两个 18001 日志的 sequence ID 分别是 `0x0f`（auto）和 `0x10`（固定 MSVDD）；它们是 change-sequence 实例 ID，不能直接当作 MCLK 的 API mask `0x10`。本地 `nvstatuscodes.h` 定义 `0x65 = NV_ERR_TIMEOUT`。这里的 `4000` 是 4000 ms host 超时，不能与 `4000000 kHz` 混为同一常量。

## 4. PMU 中 relation offset 已被投影成最终绝对 MCLK 请求

实际运行时 PMU：

- `/home/user/rt_5090_project/power_governor_reverse/gb202_r570215_runtime_pmu.elf`
- SHA-256 `2eef42f0b434990d2c9669124199a912e8e16d8480d1c9a74d46d75e1575b93b`

其静态 clock-domain 分发表为：

```text
PTR_PTR_202a2a70[4] = 0x202a30e0
```

单 bit mask `0x10` 的 hash/index 为 4；这正是 MCLK。对象 `0x202a30e0` 的 vtable 为 `0x202a29b0`：

```text
slot +0x08 = 0x20633630
slot +0x10 = 0x2063469e
```

恢复出的数据流为：

1. `0x2065c7a4` 从每个 12-byte domain request 取 `mask` 和 `frequency_kHz`；
2. 对 MCLK 调用 `0x20633630`；
3. `0x20633630` 读取 `*request_frequency_kHz`，需要转换时保存到 MCLK object `+0x68`；
4. `0x2063469e` 再从 object `+0x68` 取值，构造 command-0 payload；
5. `0x206358ca` 调用共享 mailbox primitive：

```c
mailbox_xfer(command = 0,
             payload_frequency_kHz,
             timeout = 95000,
             direct = 0);
```

所以 PMU 下游看到的是最终绝对 MCLK target，不只是 MODS 打印的 relation offset。把 VBIOS relation-12 基准从 14001 改到 15001，确实可以把 19000 的表面 offset 从 4999 降到 3999 MHz，但最终仍会向该路径提交 19000000 kHz；这不是已证明的安全绕过。

## 5. mailbox busy 的前一个事务范围已缩小

共享 primitive 为 `0x205d19ce`，busy byte 为 `0x20016af8`：

- 入口发现 busy 非零：在 `0x205d1a2c` 执行 `ebreak`；
- 成功完成后才在 `0x205d1b36` 清 busy；
- 命令号还必须 `< 5`。

整个 runtime PMU 只有两个直接调用者：

1. `0x206358ca`：command 0、timeout 95000；
2. `0x20686a62`：command 3/4、timeout 300、direct mode。

故障 mailbox 栈：

```text
0x205d1a2c
0x20635920
0x20634728
0x2065cadc
0x2063805c
```

精确落在第一条调用链，即当前撞锁者是 MCLK command 0。由于 primitive 的其他唯一调用者是 `0x20686a62`，一直持有 busy 的首个事务必然是较早的 command 3 或 command 4。

`0x20686cac` 的正向状态机在 phase 12 调用 command 3；回退/拆除路径调用 command 4。结合这是从 14001 向 18001 MHz 的上调，command 3 是首个未完成事务的较强候选。不过现有故障转储没有保存请求寄存器原值，也尚未把该状态机对象与本次 MCLK sequence 做成完全无间接边的绑定，因此 3/4 的区分仍不能视为闭合事实。

## 6. 为什么 VBIOS 显示 +5000 仍可能在 +4000 失败

在本地 ASUS ROM 对照中：

- 较早/普通范围 ROM：MCLK `-1000..+3000 MHz`；
- 当前匹配 ROM：MCLK `-1000..+5000 MHz`。

两者的 Clocks 表只需修改 packed range 元数据（同时还有 GPC range 改动和镜像副本）；MCLK Clock Programming 表与 4 KiB PLL-info 区完全相同：

```text
Clock Programming SHA-256
980da2f7ecb733aee33977cb8b7a33b8a36d0acfc2b922900763f901203525b9

PLL-info 4 KiB SHA-256
31060ff086a4c1574f65a1587d4108d173e05e3197f144728f0bef64fee1766e
```

这证明把公开 offset 上限从 +3000 扩到 +5000，并没有同时增加新的 Clock Programming 键或替换该 PLL-info 区。它不证明所有 GDDR7 timing/training 数据都相同，但足以说明“host 广告范围扩大”不等于“整个下游 change-sequencer 路径已支持 38 Gbps”。

两个 PMU ELF 都不存在原始 32-bit `4000000`、`18000000` 或 `18001000` 常量。边界可能来自运行时导入数据、外部 mailbox consumer、压缩/派生比较或 GDDR7 change sequence 状态；不能声称 PMU 主 ELF 内有一个简单的 `if (offset >= 4000000)`。

## 7. 38 Gbps 路径评估

| 方法 | 能否表达数值 | 是否避开故障路径 | 静态安全结论 |
|---|---:|---:|---|
| relation 12 直接写 `4999000 kHz` | ABI 能表达；host 广告范围看似允许 | 否 | 不安全/很可能复现同一路径 |
| 分两次写较小 offset | 能写两次 | 否；setter 替换完整 control state，不累加 | 不是绕过 |
| 把 relation-12 基准改高，再用 `<4000000` offset | 表面上可表达 | 否；PMU 收到最终绝对 target | 未证明安全 |
| 改用 CLK_DOMAINS MCLK offset | 对象广告到 +5000 MHz | 未证明；最终仍进入 MCLK physical/change sequence | 未证明安全 |
| 直接 PLL/MMIO | 可能写出某个 divider | 会绕过正常转换/训练/校验 | 不应作为安全方案 |
| 配套更新 VBIOS + PMU/外部 mailbox consumer | 理论上可行 | 可以真正修复 | 需要厂商级固件与硬件验证 |

因此当前唯一有证据支持的保护值仍是：

```text
relation 12 total offset < 4000000 kHz
本机已验证上界：3999000 kHz
对应请求：18000000 kHz（36 Gbps 标称）
```

这只是避免已知控制路径故障，不是对长期显存稳定性的普遍保证。

## 8. 建议修复

### MODS / host RM 防崩溃修复

在 `Perf50::adjust_dram_vfrels`（`0x16b15c0`）写回 relation controls 前，或在 host RM VF-rel SET validator 中增加 build/chip-aware physical-limit 校验：

```c
if (chip == GB202 && runtime_pmu_build == affected_build &&
    relation == 12 && offset_khz >= 4000000)
    return NV_ERR_OUT_OF_RANGE;
```

更好的实现是根据 PMU/FB change-sequencer 实际能力取得 target 上限，而不是硬编码本卡数值。该补丁只能把 crash 变成干净拒绝，不能启用 38 Gbps。

### PMU 恢复性修复

- `0x205d19ce` 遇到 busy 时返回 `NV_ERR_BUSY`/`NV_ERR_STATE_IN_USE`，不要 `ebreak`；
- command 3/4 失败或超时时必须释放 owner 状态并完成回退；
- command 0 与 command 3/4 应串行化或排队；
- change sequence 在启动 transaction 前验证最终 MCLK target；
- 若硬件确实支持 19 GHz，必须同步扩展 command-3 consumer、clock programming、GDDR7 timing/training 和恢复路径。

不能只把 `ebreak` NOP 掉：那会在 mailbox owner 未释放时继续操作共享寄存器，风险高于当前可见的 fail-stop。

## 9. 仍未闭合的最小问题

1. 首个 owner 在故障实例中究竟是 command 3 还是 command 4；现有静态/方向证据偏向 command 3。
2. `4000000 kHz` 首次改变下游语义的位置是在 PMU 运行时导入数据、外部 mailbox consumer，还是 GDDR7 change sequence 的派生状态。
3. 19 GHz 是否需要新的 GDDR7 timing/training 档，而不仅是 PLL 能否产生目标频率。

这三个问题没有闭合前，不应把任一 setter、VBIOS 基准修改或直接寄存器写入称为“安全的 38G 方法”。
